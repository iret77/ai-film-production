# Workflows: The Typical Jobs, as Runbooks (ch. 25)

Named, ordered procedures for the recurring jobs of an AI-film production. They add NO new rules — they chain the existing chapters into the order that has proven to work, so a session never improvises the sequence. Every step that writes a prompt runs the per-prompt checklist (SKILL.md); every workflow ends by updating the production bible (SKILL rule 11). Every external generation/edit first receives a RECEIPT line (SKILL.md Scope & version; state `live-checked <date>` or `from reference <KEY>`, SKILL rule 16) in that bible. Pick the workflow by trigger; if two apply, run the earlier-numbered one first — except W10, which is a production MODEL: when a project runs storyboard-first, W10 is the spine and calls W1–W3 and W7 at the stages it names. Citations: `production-pipeline ch. N` for chapters 1–11, `<file> §N` for section-numbered files (SKILL.md citation convention).

## W1 — New project (trigger: a new film/short/ad/social video begins)
1. Genre named or evident? Read `genre-baselines.md` FIRST — it pre-answers craft defaults and names the files THIS project type needs.
2. Story intake gate (story-structures ch. 23a): the story comes from the user; offer a dramaturgical container before any craft settles.
3. Settle only what the conversation hasn't: format/look (stylized and UGC absorb errors; photoreal demands discipline; ~70% realism is the uncanny danger zone) · target length & platform · deliverable · model stack (renderability §6 quick profiles, production-pipeline ch. 5) · dialogue language + route (native test take / audio dub / video dub — SKILL Workflow 1). Interaction contract (SKILL.md Workflow 1): one grouped question message, then ASSUMED defaults, logged in the bible decision log.
4. Style direction: user names a director/DoP or a mood → W7.
5. Create the production bible (ch. 22, template 22b) BEFORE the first asset order — every project, even one that looks like a single session (SKILL rule 11); register the decisions above as canon. The bible's Verify-line row is never left empty: with a recipe, copy its Verify line; without one, write a DEFAULT VERIFY LINE of three binary checks derived from the style anchor and the genre baseline defaults, e.g. "palette = anchor palette? · key light from the stated side and motivated? · sequence camera grammar as planned?" — label it DEFAULT so W7 can replace it if a recipe is chosen later.
Exit: bible exists, container chosen, look decided, model stack named (Render-ID tokens fixed in bible section B1), Verify line present.

## W2 — Asset & reference-pool build-out (trigger: project has a bible, no approved assets yet; or a new character/location/prop enters)
1. Order of build per the production-pipeline ch. 1 build-order rule — case (a) default: location plates → characters → props → composite stills; case (b) stylized 3D/Pixar: character sheets first, figure-anchored plates, then derived empty plates (pixar-look §8); case (c) any project with a blockout stage (W10): sheets → blockout → plates.
2. Per character: minimal sheet (or animation variant: 1 pose + 8 expressions), defensive anatomy locks, one-face rule, iterated to the anchor standard (production-pipeline ch. 3). Persistent state changes = NEW state sheets, never prompt adjectives. Each order ships as a Render Slate + still prompt (asset order shape, production-pipeline ch. 3).
3. Per location: master wide + 2–3 detail plates at ONE exposure; decide reverses UP FRONT (production-pipeline ch. 4 / ch. 16 — late reverse plates are the most expensive single mistake; in a storyboard-first project the camera setup system of ch. 2 IS this decision). Location needs counter-angles (dialogue, cross-room action)? Produce the plates NOW at rung-3 tools — a purpose-built angle tool IF the live Higgsfield shell has one (production-pipeline ch. 16 tool section: undated, verify in the tool picker and mint a fresh receipt first) or GPT Image 2.5 WITH the layout map or master plate as input, never free-text "same scene from behind" — and reverse-test against the master (anchors, openings, light side, palette; production-pipeline ch. 16 rung 3, platforms-models ch. 13b). The coverage ladder of W6 is for angles needed on an EXISTING take; it does not delay planned plates.
4. Build the reference POOL as a deliverable (ch. 14b) = the bible's asset registry (section B3): wardrobe details, prop stills, style stills, motion clips, voice/audio refs, clay blockouts — one reference for every element that must stay consistent anywhere, each row carrying its reference class (@Image / @Video / @Audio / @Clay Render).
5. Register everything as named elements with EXACT tag names (@hero, @loc_x, @anchor_1A); a name mismatch silently unbinds (production-pipeline ch. 5b; token form per surface: video-prompting ch. 12b).
6. Lock gate per LEAD asset (recurring characters, hero locations, hero props): ten-of-ten stress test (production-pipeline ch. 3 — ten generations with the sheet attached, varied pose and light, recognisable in ten of ten; run as image-model stills at draft tier — the cheap form — a fail means the description/sheet is wrong, not the model: fix and re-run). Only after it passes may the bible status move approved → locked (user approval still required, bible rule 3); cameos, extras and one-scene props stop at approved. The motion ladder is the STYLE/model gate and runs once per model in W7 step 4, not per asset.
Exit: every element the script needs exists as an approved, tagged reference; leads have passed the lock gate; bible asset registry updated.

## W3 — Produce one shot (trigger: a numbered shot needs its first take)
1. CANON: read the beat in treatment/script/bible (rule 13; canon-bound vs craft-fillable content per rule 13) — content before platform, same order as the per-prompt checklist.
2. ROUTE RECEIPT: mint or reuse the project KEY and write its RECEIPT line (SKILL.md Scope & version) in one of its two states — `live-checked <date>` when you or the user read the live form in THIS session, else `from reference <KEY>` with the stored key's own date. A from-reference receipt (rule 16) is enough to draft; live confirmation is the Generate-time gate, done by whoever has the form open. Do not choose controls until the receipt exists.
3. Lint the shot against `renderability.md` (red list §2, rescues §3) — rewrite or attach a rescue BEFORE spending a render.
4. Stills-first: generate the shot's still (per-prompt checklist; style mechanics per style-control §2–4 for the routed model) → user approves → register as `@anchor_<shot>`.
5. Motion test as a BATCH OF 4 at draft resolution (480/720p, 10 s; production-pipeline ch. 10 batch protocol — watch all four fully: one odd take is a roll, four are the prompt) with the anchor attached as a tagged reference, take opening in motion (start-frame slot only for rule 1's two cases — say which path in the slate); judge with the project's Verify line (recipe's, or the default line from W1 step 5) + shot criteria (review loop, production-pipeline ch. 1; verdict order post-audio-legal ch. 19). When the agent cannot view the result, the director answers the six passes (SKILL checklist step 7).
6. Production take only after the motion test sits: target resolution, full duration — a new generation of the locked prompt (same Render ID, new settings row), not an extension of the draft take. **Exception (🟡 [PP]):** when the target-resolution generation loses scale or structure the draft had, route draft → scoped `video_edit` / upscale (W5, post-audio-legal ch. 17) instead of rerolling — a new Take ID (bible rule 3); offered, never forced, and draft pixels never go into the final. A defect accepted at the still stage propagates — surface that trade-off, the user decides.
Exit: approved take; anchor + statuses + render/take log rows in the bible.

## W4 — Build a scene/sequence (trigger: several shots of one scene; anything longer than one take)
1. Plan in shots (4–12 s), generate in takes: 1–3 internal shots per take (single shot for calm single-event beats, 2–3 only where a cut is needed for pace or coverage — production-pipeline ch. 2), every internal shot's anchor attached and time-scoped (production-pipeline ch. 1), explicit ENDING STATE, never a dramatic peak at a take's end (SKILL rule 2, ch. 14).
2. Chain takes with state chaining: each take's prompt begins from the previous ENDING STATE ("continue forward, do not replay"). Pick ONE join mechanism per model, never both for the same join: Seedance 2.5 → `video_extension` (30 s base + ONE extension round ≈60 s, boundary-frame contract each round from the last CLEAN frame of the raw export, then re-anchor a NEW generation from the original references — ch. 14b; no cold stitching, no harvested start frame; harvest the source's last frame only to WRITE the boundary state); models without a native extension mode (Seedance 2.0; check renderability §6 for others) → harvest the final frame as the next take's start frame — the chain case, the one place a start frame is doctrine; outside chained continuation the anchor is a reference, not a start frame (production-pipeline ch. 1).
3. Dialogue scenes: shot/reverse-shot with the multi-plate set + 180° lock (production-pipeline ch. 7; multi-plate set platforms-models ch. 13b); strongest lock = 3D blockout path (production-pipeline ch. 8). No recipe overrides the in-take axis lock (director-recipes header).
4. Assemble; the score is built in post — never in the video model (rule 9).
Exit: scene cut together from approved takes; continuity ledger (bible section B7) updated (ch. 19).

## W5 — Repair a faulty take (trigger: a take that passed the hard rejects and won its batch by emotion — post-audio-legal ch. 19 verdict order — has a local fault)
Seedance 2.5: never reroll an approved take for a local fault (rule 12) — route by the table. Other models: use the last two rows.
| Fault | Fix |
|---|---|
| Wrong object/face/detail in a region or time window | `video_edit`, region description + explicit time scope (ch. 14b/14) |
| Right performance, wrong camera | camera-perspective edit — segmented camera plan, everything else locked (ch. 14b); [PP]-unproven, one test, then rung 3 of W6 |
| Right performance, wrong environment | green-screen relocation via `omni_reference` (ch. 14b) |
| Wrong subject, right timeline | subject swap + Timeline Inheritance clause (ch. 14) |
| Audio only (music/voice/language/SFX) | audio-category edit — never touch pixels (ch. 14b) |
| Too short / scene continues | `video_extension` with boundary-frame contract (ch. 14b) |
| Wrong object, prop, wardrobe or location in an existing clip, any model's output, on Higgsfield | **Genjutsu — Object Swap** (Video → model selector → Genjutsu; one clip ≤30 s + up to 30 reference photos, output ≤1080p; `HF-WEB@2026-09-04`, changelog 2026-09-01) — untested here [🟡]; confirm the live form and treat the result as a new Take ID |
| Model/surface has no scoped edit route for this fault (Seedance 2.0, Kling, Veo, Grok; check the model's quick profile, renderability §6, and the surface in platform-ui-workflows — Runway = Aleph 2.0 Edit Studio, H3 = V2V edit) | harvest clean 2–4 s as coverage (production-pipeline ch. 10), fix the weakest instruction, regenerate; `extend` only where the model offers it (Veo 3.1, Seedance) |
| Fault is global (style, light, physics everywhere) | back to the prompt: fix the weakest instruction, regenerate (production-pipeline ch. 1 review loop) |
Constraints (ch. 14b): source ≤20 s recommended, 1–5 refs; edits bill the source's full duration; ≤3 edit rounds per source, then branch from the best intermediate .mov export as the new @Video 1 (ch. 14b edit-round ceiling). Every edit result is a new Take ID (bible rule 3).
Exit: fixed take approved; its RECEIPT KEY and render/take log row noted in the bible.

## W6 — Get a new angle / coverage (trigger: a reverse, insert, or B-camera view is needed on an EXISTING take or approved still set; planned reverse plates for dialogue/cross-room sets are pre-production → W2 step 3)
Climb the ladder, exhaust each rung (ch. 16):
1. New angles as internal shots of the SAME take (cheapest, most reliable).
2. Harvest frames from an existing successful generation as references (last frame + "continue forward, do not replay"); or ONE camera-perspective edit on the approved take (B-camera pass — [PP]-unproven, budget one test only, bills the source's full duration; ch. 16 rung 2, ch. 14b). A failed single test → rung 3, not a second edit.
3. Still needed as a STILL: a purpose-built angle tool IF the live Higgsfield shell has one (production-pipeline ch. 16 tool section: undated, verify in the tool picker and mint a fresh receipt first) or GPT Image 2.5 WITH a layout map — never free-text "same scene from behind". Reverse test: anchors, openings, light side, palette against the master plate.
4. Nothing pins → geometry inputs: 3D blockout/clay render (production-pipeline ch. 8; video-prompting ch. 14b).
Exit: coverage that passes the reverse test.

## W7 — Define & lock a style (trigger: user names a director/film/mood, or the look drifts)
1. User names a direction → `director-recipes.md` selection index; cap = ONE director recipe + at most ONE DoP signature (two packages, one dominant); two directors named → synthesis (selection index step 6), never two recipes side by side.
2. Build the project style anchor (the style-contract paragraph) from look-defining references via LLM reverse-engineering (style-control §7), or from the vocabulary packages (style-control §6) — plus its 4–8 look tokens (SKILL.md Workflow step 4).
3. Stylized 3D: figure anchor or style-forcing blocks (SKILL rule 8; pixar-look §8/§9).
4. Validate on ONE still + one motion-ladder test per model before rolling out (style-control §5b); the recipe's Verify line becomes the standing reroll gate (replacing a DEFAULT line from W1 step 5).
5. Write the final style anchor + look tokens into the bible (section B2); from then on it is canon, distributed into every prompt per SKILL.md Workflow step 4.
Exit: style anchor + look tokens + Verify line in the bible + a passing verify still.

## W8 — A generation keeps failing (trigger: one prompt has failed on the same axis on a full batch of 4, or two iterations in a row)
1. Suspect the PROMPT first (in first-party production sessions [PP, 🟡 heuristic, not a measured statistic] roughly 8 of 10 presumed model limits were prompt faults, SKILL rule 14): lint for internal contradictions, missing positive lock on the failing axis, stacked instructions on one axis, meta commentary (ch. 24b).
2. Count in ITERATIONS (one prompt revision judged on one batch of 4, production-pipeline ch. 10): one or two weird rolls are rolls — reroll; four bad rolls = a failed iteration. Iterations 1–3: surgical fixes, one line per iteration.
3. After the 3rd failed iteration: rewrite short from scratch AND change CHANNEL, not vocabulary: reference/sketch/mask/clay render/seed reroll/other model (ch. 24b contract item 7; stills ladders ch. 24c–g; video ch. 14b).
4. Only after that clean minimal prompt fails twice on the same axis (two clean iterations, at least two channels): declare a model limit, route the shot to another model (renderability §6) or rescue/rewrite the beat (renderability §3 rescue paths). Flag a kept risk in the delivery risk register (SKILL rule 10) and, at close, in the shot board's Risk → rescue cell.
5. Budget per shot across all steps: 10–15 iterations → simplify the SHOT (split it, remove an action, change the angle), not the words (production-pipeline ch. 10).
Exit: working result, or a documented model limit with a rescue.

## W9 — Session open & close (trigger: every working session in an existing project)
Open: load the production bible FIRST (rule 11); read only the files the active runbook step names; revalidate the RECEIPT line (SKILL.md Scope & version) for every active generation route before relying on a control — state `live-checked <date>` only for a form actually read this session, otherwise keep `from reference <KEY>`.
Close: update the bible LAST — add each actual generation/edit's KEY and render/take log row (section B4b) to the shot board and the delivery's Render Slates; statuses only on user approval, decisions as canon, open risks into the shot board's Risk → rescue cell (copied from the delivery risk registers); reviews the agent could not perform as `TKnn — review pending (director)` in Handoff; nothing outside the bible is canon. Offer ONCE per project (bible decision log: `feedback-to-skill offer: made / declined`) to feed genuinely new production findings back to the public skill (generalized, no project content — SKILL.md closing section).

## W10 — Storyboard-first production model (trigger: a new project adopts the storyboard-first model; "how do we go about this" / "wie gehen wir vor"; any project with more than one camera axis per location, vertical geography, or a documented geography drift between takes)
Nine gated stages (stage 4, the animatic, is optional — the director may skip it on a short single-axis project; record the skip in the decision log). Each stage names its **Deliverable**, its **Gate** (what must exist before the next stage starts — a gate not passed means the next stage does not start) and its **Reads** (the only files opened in that stage). W10 adds no rules of its own: every rule it applies lives in the chapter it cites (build order ch. 1, anchor standard ch. 3, blockout trigger ch. 8, storyboard roles ch. 9, deliverable shape ch. 2, production-take exception W3 step 6); W10 fixes the ORDER in which W1–W3 and W7 run and inserts the three planning artefacts (camera setup system, take/cut table, timed animatic) the later stages consume.

1. **Idea & brainstorming** — the director brings the idea; the agent moderates (story intake gate story-structures 23a, container offer 23f, causal change lint 23g). Reads: `genre-baselines.md` if a genre is named, `story-structures.md` 23a/23f/23g. Deliverable: logline + beat chain as a DRAFT proposal (SKILL rule 13), every beat written cause→effect (rule 15). Gate: the director confirms the logline AND the beat chain; an unconfirmed beat is not drawn in stage 3.
2. **Project briefing / bible** — create the bible (production-bible 22b) with story, look contract (W7 if a style is named), character/location/prop list (names + planned statuses), format, length, platform, model stack (W1 steps 3–5). Reads: `production-bible.md` 22a/22b, `renderability.md` §2–3, W1. Then the **renderability lint of the briefing**: classify EVERY beat against the renderability §2 rows — in particular "Physics as hero", "Tiny hero object", "Dark, figure-less macro", "Continuous approach over distance", "Cut back onto the same emissive object", "Long continuous camera moves", "Wide shots". Every red beat receives an ellipsis or still rescue (renderability §3) or is cut — BEFORE the storyboard. Why: these beat classes are the documented time-eaters; a storyboard that draws them plans shots that never come out. Deliverable: bible B1–B3 filled, beat-level risk register (SKILL rule 10 shape, Decision column filled by the director). Gate: bible exists; no beat is red without a decided rescue.
3. **Storyboard = shot planning** — deliver the STORYBOARD of production-pipeline ch. 2, all four parts: (1) camera setup system per location, (2) look-free panels with setup tags and a/b pairs, (3) take/cut table with the state ladder, (4) layout map — and the ranking stated there (setup system + table + ladder + anchors bind; panels are the director's checking view). Reads: `production-pipeline.md` ch. 2 (shape, rules, export schema), ch. 4 (the setup system IS the reverse decision), ch. 8 (layout map), ch. 9 (storyboard roles; grey sketch template); `film-craft.md` for coverage grammar. Tool: **FilmFlow Pro** (`FILMFLOW-WEB@2026-09-07`, platform-ui-workflows ledger) is the recommended environment for stages 2–3 IF (a) its frames stay look-free (sketch/clay, no rendered look) and (b) it yields an agent-readable export in the ch. 2 schema; otherwise a Markdown shot board + grey image-model sketches. Gate: director sign-off on all four parts; the storyboard is linked in bible section B3b with version and sign-off date. From here every prompt is written from panel + setup line + take row — never from prose.
4. **Animatic — timing & montage simulation (OPTIONAL, before the sheets)** — play the storyboard as a TIMED reel to test montage, order, rhythm, causality and per-shot duration BEFORE any consistency asset is built. Each panel (or a/b pair) is held for its take-table `Len`; scratch audio (VO + temp music + timing markers) sets the true minimum durations — dialogue length is only real once spoken (SKILL rule 2: the take's `Len` is where this locks). Why HERE, before the sheets: the animatic needs NO final designs — only the load-bearing aspects of figures and locations sketched, i.e. the look-free panels stage 3 already produced (ch. 9 storyboard roles). Running it first is a GATE that kills, merges, reorders or shortens shots before sheet and render budget is spent on them — and the R3 rung below doubles as the earliest warning system for exactly the red-list beats (fast motion, hero physics, `Physics as hero`) flagged in stage 2, the beats most expensive to fix late. **Fidelity ladder — chosen PER BEAT (not per project); escalate only as far as the beat's open question demands:**
   - **R1 — held still + scratch audio:** order, duration, dialogue timing. Zero cost, the default rung.
   - **R2 — deterministic camera on the still** (Ken Burns push/pan/zoom, dissolves; or a first→last-frame interpolation between two panels of THIS shot — the SKILL rule 1 controlled move, not a performance): tests camera timing, reveals, cut rhythm. Deterministic, no drift, no model cost, re-editable (NLE / ffmpeg `zoompan`).
   - **R3 — sub-shot panels** (higher temporal resolution of one shot: several drawings per shot, played flip-book): tests action/motion timing for fast or complex beats — does the beat fit its seconds, or must it be split/elided (renderability §3). Three interchangeable ways to produce the in-betweens, all feeding the same reel: hand- or AI-drawn intermediate panels (deterministic, no model); cheap image-gen in the same rough sketch style; or a cheap low-res tween (480p, an old video model) / interpolation between two panels.
     - **R3 discipline (binding):** the in-betweens illustrate the ACTION PROGRESSION and TIMING only — never the performance, the optics, or the identity. Read duration and beat-fit; discard the model's specific motion. Letting a cheap tween's motion become canon plans the shot against motion the production model will not reproduce (a timing test laundered into false canon).

   Reads: `production-pipeline.md` ch. 2 (take/cut table + state ladder — the animatic PLAYS this), ch. 9 (storyboard roles; panels stay look-free); `film-craft.md` (editing, rhythm, coverage grammar); `renderability.md` §2–3 (the red beats the R3 rung stress-tests). Tool: FilmFlow Pro (`FILMFLOW-WEB@2026-09-07`, platform-ui-workflows ledger) already binds panels to shots with animatic playback and per-shot timing and fits R1/R2 directly (the same surface used for stages 2–3); otherwise an NLE or ffmpeg `zoompan`. For an R3 tween a cheap video route at 480p — mint a receipt first (SKILL rule 16). Deliverable: a timed animatic reel + a **revised take/cut table** — `Len` values locked or corrected, internal-shot counts decided (SKILL rule 2: calm beat = 1 shot; dynamic/dialogue = 2–3 cuts), continuity/causality flags raised (rule 15). Gate: director sign-off on the reel; the corrected `Len` and cut points are written back into the storyboard (B3b) and the take/cut table (B4) BEFORE the sheets start. The animatic never becomes a look reference and its R3 motion is never canon — it corrects timing and cut points, nothing else.
5. **Character & prop sheets (Elements)** — BEFORE the blockout: build-order case (c) of production-pipeline ch. 1 (the blockout needs the proportions; body length is the scale unit of the layout map). W2 steps 2, 5 and 6 per character; prop sheets and state pairs per the state ladder (ch. 4). Iterate every sheet to the **anchor standard** (ch. 3: exact, never "good enough"). Reads: `production-pipeline.md` ch. 1 (order), ch. 3–4, `style-control.md` for the routed still model, W2. Gate: sheets approved (leads through the W2 step-6 lock gate), scale written as object relations in B3 (ch. 4).
6. **3D blocking / blockout** — the ch. 8 blockout, run as a stage under the **blockout trigger rule** (ch. 8: optional for one axis + flat geography, mandatory for vertical geography, several axes, or documented drift): one scene per location, every panel placed as a camera on it; viewport render per the ch. 8 blockout-video requirements (24 fps, overlays off, 3–5 s per move, ≈30 s reference budget) as the `@Clay Render` staging reference — role split blockout = camera/blocking/timing, images = look (ch. 8 mandatory companions). Tool-neutral (ch. 8 evidence tiers; Blender + Bridge MCP `HF-BRIDGE-MCP@2026-09-04` is the documented baseline). Reads: `production-pipeline.md` ch. 8, `video-prompting.md` ch. 14b (reference budgets, @Clay Render role line). Gate: blockout frames match the panels (framing, position, gaze direction); a mismatch is fixed in the blockout or marked on the panel — the panel is never redrawn to match the blockout.
7. **Location anchors** — plates AFTER the blockout (ch. 1 case (c)): the blockout frame or the layout schematic is the geography reference of the plate prompt, the look comes from the style contract (B2); light openings described as geometry per ch. 4. W2 step 3 and production-pipeline ch. 4 per location, one plate per setup that needs its own view. Storyboard panels never enter a generation (ch. 9 storyboard roles). Reads: `production-pipeline.md` ch. 4, `style-control.md`, W2 step 3. Gate: anchors exact (anchor standard, ch. 3) — light direction, scale, geography match the layout map.
8. **Test takes at draft tier (720p)** — per take W3 steps 1–5: canon from panel + take row, receipt, lint, still anchor, batch of 4 at 720p; rule-14 iteration count. Reads: W3, W4 (chaining), W8 (failing), `video-prompting.md` ch. 12/14. Gate: the STRUCTURE of the take holds — cuts land on the take-table timecodes, continuity states in and out match, identities hold. Polish is not judged here.
9. **Production takes (1080p / 4K)** — W3 step 6: a new generation of the locked prompt at target resolution by default; its documented exception (draft → `video_edit` / upscale when the reroll loses scale or structure) applies as written there. Never cut draft pixels into the final: the draft cut fixes structure, not pixels. Then picture lock → audio → grade as dated stages (post-audio-legal ch. 17/18; dates in B6, state in B8). Reads: W3 step 6, W5, `post-audio-legal.md` ch. 17–19.
Exit: storyboard, setup system and take/cut table in the bible as canon (B3b, B4 columns filled); every shot at status ≥ take; picture lock dated.

**W10 house rules** (each lives in the chapter named; listed here so a session sees them together):
- Anchor standard — iterate until exact, deadline pressure does not lower it (production-pipeline ch. 3).
- A post-state needs a visible cause in frame — break point, debris, crack — or it reads as placed (state ladder, ch. 2; state pairs, ch. 4).
- Continuity between takes = the join mechanism of W4 step 2 (keeper's end frame per rule 1) + a position lock over all internal shots + one axis (ch. 6 position lock).
- Scale only as object relations, never adjectives (ch. 4; image-model-logic 24b).
- Light openings as geometry; light-geometry words generate rays (ch. 4).
- Actions as two states, uninvolved objects fixed, gaze written after every action (ch. 6 position lock).
- Panels from an image model are independent inventions — consistency comes from the setup system on paper and the blockout in geometry; the storyboard says WHAT must stay the same, the blockout says HOW (ch. 9 storyboard roles).
- A storyboard without a camera setup system is unusable — free camera positions per panel produce the perspective inconsistency that later shows up in the takes (ch. 2).
- A storyboard is canon only when linked in the bible (section B3b); a document beside the bible is ignored by the next session.
- The animatic corrects TIMING, never look — panels stay look-free, its R3 motion is never a look or performance reference; it revises the take/cut table (`Len`, cut points, internal-shot counts) and nothing else, and runs before the sheets so it can cut or merge shots before they cost anything (stage 4).
