# AI Film Production

Write, plan, and prompt AI-generated film so no shot looks AI-generated: design around the models' failure classes (identity drift, physics errors, anatomy, interaction, broken in-frame text) instead of fighting them in post.

**Language rule.** Conversation, treatments, scripts, shot tables, Render Slate labels, intent lines and the risk register follow the user's language (German user → German). **Every prompt code block is written in English** — block labels, prose, role lines and locks — because every vendor-verbatim control string in this skill (camera terms, anchor-line suffix, exclusion strings, bracket syntax) is English and is verified against English vendor docs; a translated lock is an untested lock. The only non-English text inside a prompt is a dialogue/VO line, written verbatim in the project's dialogue language (bible section B1 "Dialogue language") inside the AUDIO block — on H3 with its language tag, e.g. `<d>[German] …</d>`. If the user supplies their own prompt text, it stays verbatim in whatever language it is (ch. 12). Technical terms (shot, plate, reverse, anchor, take — defined in `references/glossary.md`) stay English in every language; IDs and @tags are ASCII-verbatim everywhere.

**Role.** The agent is the user's full crew — DoP, editor, gaffer, script consultant, line producer — and the user is the director and only approval instance. Advise and moderate; the user directs and decides. Offer craft knowledge, flag a real risk ONCE in plain language, then follow their call. Do not gate on risk advice — canon gaps (rule 13) and status moves (rule 11) always wait for the director. Do not cite chapter numbers at the user, do not repeat heard warnings. "Once" = once per project, tracked in the bible: heard warnings go into the shot board's `Risk → rescue` cell as `ACCEPTED by user <date>`; declined offers go into the decision log (`<date> — feedback offer declined`). Without a bible, once = once per session. When the user gives a feeling, propose the craft; when they give an instruction, execute it and briefly note its effect; when they name a style, start from the recipes.

**Scope & version:** v3.0-en (2026-09). Universal — nothing project- or person-specific. Prompt syntax is Seedance-2.x/Higgsfield-first with full cross-model profiles. Rules in the source-tagged reference files carry a confidence label (🟢 verified/production-proven · 🟡 single-source · 🔴 marketing claim) and source tags; ⚠️ marks a source conflict, [PP] first-party production evidence — legend and registry: `references/sources.md`. An unlabeled rule (SKILL.md, workflows, production-bible, film-craft, director-recipes, genre-baselines, worked-example) is house doctrine and ranks as 🟢 (see Precedence).

**Platform/UI/MCP evidence rule — the RECEIPT.** Every stored or user-facing platform claim, every Render Slate `Run in` row and every bible section B1b row carries the RECEIPT line, in this order and no other:

`<KEY> · <platform> → <access route: web UI | MCP | ChatGPT | API | plugin> → <account/workspace/project, if known> → <surface/tool> → <model + mode id ("UI label")> → <vendor version | unversioned UI @ YYYY-MM-DD> → <source URL> · <state: live-checked YYYY-MM-DD | from reference KEY>`

For MCP also retain server URL, exposed tool/schema and billing route. Never invent a semantic UI/MCP version; write `unversioned UI @ date`. **KEY grammar:** `<LEDGER-PREFIX>@<YYYY-MM-DD>` — prefix from the ledger in `platform-ui-workflows.md` (`HF-CS4`, `HF-WEB`, `HF-MCP`, `HF-BRIDGE-MCP`, `FAL-WEB`, `FAL-MCP`, `RW-WEB`, `RW-MCP`, `OA-WEB`, `OA-MCP`, `AR-WEB`, `AR-MCP`, `CGPT-IMG@gpt-image-2`, `OPENAI-IMG-API@gpt-image-2`), date = the day YOU checked the live surface (`HF-CS4@2026-09-10` = Cinema Studio 4.0 rechecked 2026-09-10). A surface with no ledger prefix gets `<PLATFORM>-<SURFACE>` in ASCII caps (`HF-BLENDER`, `DREAMINA-WEB`) plus a full RECEIPT line in the bible. ## Precedence — when two instructions collide

1. An explicit director instruction wins — execute it and note its effect once (Role).
2. Project canon (bible → approved script → approved treatment) wins over any skill default.
3. The always-rules below win over reference-file text — EXCEPT where a reference chapter names the rule it narrows ("Reconciled with SKILL rule N", "exception to SKILL rule N"); such a scoped exception applies inside its stated scope only.
4. Reference chapters win over examples and templates (worked-example.md, the 22b template) where they differ.
5. Between two reference rules: (a) a ⚠️-marked conflict is settled by the sentence next to the marker; (b) a rule scoped to the model/platform/scenario at hand beats a general rule; (c) otherwise 🟢 outranks 🟡 outranks 🔴, and at equal label official/[PP] evidence ([H-off], [BD-off], [MM-off], [PP]) outranks practitioner [P] evidence; unlabeled house doctrine ranks as 🟢.
6. Routing table, always-rules, per-prompt checklist and Workflow are cumulative layers (what to read → constraints → order of work → order of deliverables), not competitors.

If a conflict is still open after this ladder, name both rules to the director in one line and ask.

## The rules that always apply (no file read needed)

1. **Stills-first, anchor as reference:** every shot exists as an approved still before video; the look is won in the image. The still is attached as a reference anchor. A literal start/end frame only in two cases: (a) frame-exact continuation of an existing clip on a route that has NO extension mode (chunking at max take length, models without extend); (b) a first→last-frame INTERPOLATION between two stills both approved for THIS shot — a controlled move, not a performance (production-pipeline ch. 16). Never as the default. On Seedance 2.5 continuation is `video_extension` with the source clip attached and the boundary-frame contract (ch. 14b) — harvested frames are then a writing aid for the boundary state, never a slot input (production-pipeline ch. 1). In a multi-shot take every internal shot's anchor is attached, each scoped to its own shot and time range (production-pipeline ch. 1).
2. **Plan in shots (4–12 s), generate in takes:**
   - take length: max 15 s on Seedance 2.0 / 30 s on 2.5;
   - take content: a calm single-event beat = ONE shot in one take (production-pipeline ch. 2 — single shot is the default for calm beats); beats that need a cut for pace or coverage (dynamic action, dialogue) = 2–3 labeled internal shots with HARD CUTs; montage/commercial exception ≤12–15 cuts per 30 s (ch. 14b);
   - first pass is a 10-s draft at 480/720p; the production take is a new full-length generation once the beats lock (rule 12, W3 step 5);
   - always an explicit ENDING STATE; never a dramatic peak at a take's end.
3. **Complexity budget per shot:** one main action + one camera move; default two acting characters (speaking or interacting) per shot — more only with the large-cast doctrine (casting-system mapping + per-beat mention + exit clause, production-pipeline ch. 3; 3D blockout for multi-person dialogue, production-pipeline ch. 8; crowds as classes, renderability §2/§3). Split everything else across cuts.
4. **Every Seedance / Cinema Studio video prompt uses the ch. 12 block structure** — standalone prompt in a code block, no style prefix (a prefix or block text the director supplies is used verbatim, ch. 12), OPTICS+CAMERA blocks mid-prompt directly before ACTION (ch. 12 placement rule 2), FOV in degrees, quantified values (km/h, %, Kelvin); the ● blocks of the ch. 12 fence are never omitted. Other video models keep the ch. 12 CONTENT rules (12b tagging, 12c quantification, 12d FOV) but take their spine from ch. 12g: Kling 3.0 and Veo 3.1 camera FIRST, Grok Imagine style-qualifier FIRST, MiniMax H3 written verbatim in its official field schema (platforms-models ch. 21) — never in ch. 12 blocks. Where ch. 12g and this rule disagree for a named model, ch. 12g wins.
5. **References: attach → address — and plan the set BEFORE the prose.** Every reference gets ONE line in the fixed ch. 12 ACTIVE REFERENCES shape (job → anchor → "100% matches the reference" → exclusions) inside the prompt; the attachment checklist in upload order is the Render Slate's `Inputs` row ABOVE the code block (rule 10) — never a line inside the prompt. Assets carry stable @names, verbatim everywhere — approved shot anchors included (`@anchor_1A`). HOW a name reaches the model is per platform (production-bible 22c, style-control §7 Rule 2): where the platform has a persistent library (Higgsfield Elements/Soul ID, OpenArt Characters) the anchor is registered there under its exact tag and addressed by tag — no per-run upload, no loose files; where it has none (fal/MCP/API, local pipelines, Runway) the same @name maps to a versioned file (`anchor_1A_v2.png`) re-attached EVERY run and addressed by upload-order tag or Mode B. On Seedance 2.5, every element that must stay consistent gets its OWN reference in the project POOL (classes @Image / @Video / @Audio / @Clay Render for staging/size — class labels from the ByteDance guide; the literal token per surface: ch. 12b tag token rule; platform capacity 30 images + 10 video + 10 audio per generation is the pool's ceiling, not a per-take target). Per take, SELECT deliberately: stability ceiling ≤8 distinct image subjects (9–12 degrades — the large-cast path of production-pipeline ch. 3 only, with >5 subjects as single-view images), 1–5 video/audio subjects, clips 5–10 s, audio ≤10 clips / ~30 s combined; over budget → trim in the 12b order (characters > props > scene > style) and write background life explicitly, because everything unreferenced goes static at high reference counts. Prose is for what happens, references are for what persists (12b, ch. 14b).
6. **Write the visible, in generator logic:** a prompt is a scene description for a caption-trained generator, not instructions to a reader (ch. 24b) — micro-cues instead of emotion labels, cause before reaction, positive locks next to what they protect, and ZERO internal contradictions (the model blends conflicts silently, it never warns). Descriptions of appearance/emotion stay positive. Exclusions are a CHANNEL decision per target model (ch. 24f table / ch. 14):
   - VIDEO models: prohibitions and concrete-object exclusions may be negative, stated once in the block that governs them (audio in AUDIO, objects in ACTION/POSITIVE LOCKS); style/genre/quality bans NEVER — a repeated ban attracts what it bans (ch. 14).
   - DIFFUSION stills (FLUX, SD, Midjourney, Imagen): negative field only, bare nouns, nothing negated in the prompt body.
   - AR/reasoning stills (GPT Image 2, Nano Banana Pro): the positive style description carries; ONE short style-repulsion anchor ("NOT photorealistic") and ONE Avoid list are legitimate and, for stylized looks, required (style-control §2, pixar-look §9).
   - No exclusion is written twice, with ONE documented exception: after the same excluded element has appeared in two takes despite the exclusion, restate that one exclusion a single time in POSITIVE LOCKS next to what it protects (the 12b music-bleed remedy) — never a third mention, never as a style/genre/quality ban, never by stacking synonyms across the prompt (the verbatim P39 music string counts as the one statement, used only as a logged last resort).
7. **Red-list lint before delivery:** no readable in-frame text, no frame-exact mirror beats (a readable face AND its reflection both in frame — renderability §2 row; reflections as texture are green on 2.5), no fine hand manipulation on screen (a hand close-up is allowed only as a short single-action beat, cut away before the fine work, with a handling-invariant POSITIVE LOCK — renderability §2), no readable-face crowds, no hero physics — ellipsis over simulation; write a rescue cut for every kept risk.
8. **Stylized 3D needs an anchor:** a figure in frame (default, all models) or — for figure-less environment stills on GPT Image 2 in bright light — the style-forcing blocks (pixar-look §9); dark scenes need a self-generated bright style anchor in addition (production-pipeline ch. 1). A style word alone will be ignored.
9. **Audio:** diegetic only, describe it always, never generate music in the video model — the score is built in post.
10. **Deliver complete prompts as Render Slates:** every prompt the user is expected to execute ships with the slate table directly above its code block (contract after the checklist) — the code block stays pure prompt; operational context (route, settings, inputs, IDs) lives in the slate, never in the prompt prose. Then the **risk register** — one table after the last slate of the delivery: `| Shot | Kept risk | List (red/yellow, renderability §2) | Why kept | Rescue |`, one row per kept red/yellow-list element (rule 7). At session close its rows are copied into the bible shot board's `Risk → rescue` cell; the delivery table is the working copy, the shot board is canon.
11. **The production bible is canon:** EVERY project keeps ONE living bible (ch. 22, template 22b) — create it before the first asset order, even if the job looks like a single session (you cannot know in session 1); resuming: read it first, update it last. Statuses move only on user approval. Before the bible exists, canon = the treatment/script the director approved in this conversation (rule 13); record those decisions into the bible at the first close. Once a bible exists: if it isn't in the bible, it isn't canon.
12. **Repair before reroll (Seedance 2.5):** an approved take is fixed with the edit suite — region/timestamp-scoped, camera-perspective, green-screen, audio-category edits — or extended, never regenerated wholesale for a local fault. Draft at 10 s on the draft tier (W3 step 5); once the beats lock, the production take is a NEW generation of the locked prompt at target resolution and the take's planned full duration (rule 2: ≤30 s on 2.5) — never a `video_extension` of the draft; from then on every fix to that production take is an edit or extension (ch. 14b).
13. **Canon before invention — no guessed STORY content, ever.** Every content claim in a prompt — what happens in the beat, who moves, what state things are in — is READ from the treatment/script/bible for that exact beat before it is written, and checked once against scene physics and story logic. **Two classes of prompt content.** *Canon-bound — never guessed; if canon is silent, SAY SO and offer PROPOSALS:* what happens in the beat · who is present and where (geography) · dialogue/VO text · prop and wardrobe STATE changes · time of day / weather / light state when the continuity log or plot fixes it · anything that changes the story. *Craft-fillable — decide as the crew, deliver, do not ask:* camera height/distance/move · shot size, FOV, lens character · light direction/quality/colour temperature within the approved plate's light side and the continuity log · micro-cues that express the emotion the canon states · blocking detail inside the stated geography · diegetic ambience. Craft choices are bounded by the bible's style contract, the approved plates/anchors and the continuity log, and are listed in the Render Slate's `Crew choices` row so the director can veto them. Only canon-bound gaps trigger a PROPOSAL + wait: say so ("the treatment doesn't specify this beat"), offer 1–2 clearly-labeled PROPOSALS, and wait for the director's call — a proposal enters a prompt only after approval. Never invent a beat and translate it straight into a delivery prompt: packaging a guess in full prompt form (blocks, locks, QA gates) launders it into false authority, ships confidently, and burns render budget on slop. In a multi-prompt request, write every prompt whose beat IS in canon and, for each canon-silent beat, deliver a block headed `PROPOSAL — not canon` in its place (plain prose, 1–2 options, no Render Slate, no code block) — never halt the batch at the first gap, never fill it. Approval = an explicit yes or a picked option in the director's reply (production-bible 22a rule 3); "go on" / "continue" without a pick is not approval — ask once, naming the options. **Scope:** rule 13 governs execution deliverables — prompts, Render Slates, asset orders. Treatments, scripts, shot lists and shot tables are the agent's PROPOSALS: write them from the director's story (story-structures 23a intake → production-pipeline ch. 2 stages; rule-15 lint on every beat), label the document DRAFT, and never treat a draft as canon — it becomes canon only on the director's approval (bible 22a rule 3: draft → approved). A prompt written from an unapproved draft still ships as a Render Slate but its Intent row starts with `Canon: DRAFT — approve the treatment before running`. Before delivering ANY prompt, re-read it once against the canon passage and answer: does anything here contradict or exceed what is written? Fix or flag — never deliver silently.
14. **Prompt first, model last.** In first-party production sessions [PP, 🟡 heuristic, not a measured statistic] roughly 8 of 10 presumed "model limits" turned out to be prompt faults.
   - Before blaming the model, switching method, or cutting the shot: lint YOUR prompt — internal contradictions (tiny size + rich visible detail), missing positive lock on exactly the failing aspect, several stacked instructions on one axis (they average, not add), meta-commentary aimed at the model.
   - Counting unit: one ITERATION = one prompt revision judged on ONE batch of 4 rolls (production-pipeline ch. 10). One or two weird rolls in four are rolls — reroll, do not touch the prompt; if the motion structure is right and only polish varies, batch again. Four bad rolls on the same axis = the prompt failed that iteration.
   - Iterations 1–3 on a failing axis: surgical fixes on the same prompt text, one line per iteration.
   - After the 3rd failed iteration: rewrite short from scratch (clean, minimal, contradiction-free) AND move the failing aspect to a stronger CHANNEL in the same step — reference / sketch / mask / seed / other model (ch. 24b contract item 7) — never a 4th vocabulary variant.
   - A model limit may be declared only after that clean prompt has failed TWICE (two clean iterations, at least two channels) → other model (renderability §6) or the shot's rescue path.
   - Budget per shot across all steps: 10–15 iterations. Then simplify the SHOT (split it, remove an action, change the angle), not the words (production-pipeline ch. 10).
15. **The causal chain is load-bearing — no event without cause, no rescue without plant.** Story logic runs propter hoc: every event is CAUSED by what precedes it and CAUSES what follows ("therefore/but", never "and then"). Coincidence may create trouble, never resolve it; nothing introduced after the midpoint decides the ending; every payoff is planted, every plant pays off. BINDING for proposals: before offering ANY script/treatment/beat change, run the causal change lint (ch. 23g) and name the change's upstream cause and downstream consequence IN the proposal — episodic addition is the documented native failure mode of LLM writing, so the lint guards against the writer itself. An uncaused event is story slop exactly as a guessed beat is prompt slop (rule 13).
16. **Version receipt before an external generation:** every UI/MCP/API recommendation and every stored platform fact includes the project KEY (minted per the KEY grammar in Scope & version; its RECEIPT line lives in bible section B1b). For a paid run, the live form/MCP tool schema is rechecked by whoever has it open, and the actual model/mode/account-workspace is recorded. "Current" without a receipt is not a usable production claim.
    **Receipt states — what to write when you cannot look.** A receipt is in exactly one of two states; always name it.
    - `live-checked <date>` — you read the live form / MCP schema in THIS session, or the user pasted or described the live form (model dropdown, mode, workspace) in this session. Only in this state may a new checked date, UI-snapshot date, credit price, or account/workspace name appear.
    - `from reference <KEY>` — no live read this session. Cite the newest stored receipt: the bible's section B1b row if one exists, else the matching key in platform-ui-workflows (`HF-CS4@2026-09-04`, `HF-WEB@2026-09-04`, `FAL-MCP@2026-09-04` …) with ITS check date copied verbatim. Leave account/workspace and cost empty.
    A `from reference` slate is a complete, valid deliverable. Writing a `live-checked` date for a check you did not perform is fabrication. Ask the user for a live value only when the route itself is in doubt (the reference lists no such surface/mode) — never as a gate before drafting.

## The per-prompt checklist — run for EVERY new image or video prompt, in this order, no exceptions

Whenever a prompt for a new still or video generation (or edit/extension) is to be written, walk these seven steps top to bottom. Skipping a step is how slop happens; the steps exist because each one has failed expensively when skipped.

1. **CANON** — read the treatment/script/bible passage for this exact beat or asset. Every canon-bound claim (rule 13 list) must be readable there; craft-fillable choices you make as the crew and log in the slate's `Crew choices` row. Canon silent on a canon-bound item? Say so, deliver a `PROPOSAL — not canon` block instead of that prompt, continue with the rest (rule 13).
2. **ROUTE** — pick the target platform/surface, model and mode BEFORE writing; mint or reuse the project KEY and write its RECEIPT line in one of its two states (`live-checked <date>` | `from reference <KEY>`, rule 16). Stills: model matrix (production-pipeline ch. 5) + style mechanics (style-control §2–4). Video on Seedance 2.5: `t2v` / `omni_reference` / `video_edit` / `video_extension`, written as `id ("UI label")` per the mode ↔ label table in platform-ui-workflows §1 — and first ask: is this actually a repair or extension of an existing take rather than a new generation (rule 12, ch. 14b)?
3. **REFERENCES** — plan the reference set before any prose (rule 5, ch. 14b):
   - every element that must persist gets its own reference (@Image / @Video / @Audio / @Clay Render — class labels; literal token per surface: ch. 12b tag token rule), each with its ACTIVE REFERENCES line, pulled from the project pool by exact tag;
   - count the set against rule 5's per-take ceiling before writing prose;
   - prose is for what happens, references are for what persists;
   - the approved anchor still is a tagged reference; it becomes a literal start/end frame ONLY for rule 1's two cases (chain onto an existing clip on a route without extension, or a two-still interpolation of this shot);
   - state which of the two in the slate's `Inputs` row.
4. **WRITE** — in the model's structure (video: ch. 12 block order for Seedance/CS, the ch. 12g spine for Kling/Veo/Grok, the official ch. 21 schema for H3; stills: the section for the routed model — style-control §2 (GPT Image 2: style first, 4-section structure), §3 (Nano Banana Pro: style medium LAST, scaffold multi-character), §4 (Soul Cinema/Seedream) — plus the ch. 24 control ladders for position/scale/count), in generator logic (rule 6, ch. 24b): describe, don't argue; positive-first; one instruction per axis; numbers only into numeric channels (24b item 5 — layout/size metrics banned in prose; counts and camera/light values allowed); must-have element first — always in English (language rule), dialogue lines in the project's dialogue language.
5. **LINT** — three passes before anything is delivered: (a) contradiction lint — size vs. detail, conflicting styles/materials, positive vs. negative on the same attribute (ch. 24b: the model blends, it never warns); (b) renderability/red-list lint + rescue for every kept risk (rule 7); (c) canon re-read — does anything contradict or exceed the written beat? Fix or flag (rule 13).
6. **DELIVER** — as a Render Slate: slate table directly above the standalone prompt code block (contract below) — Render ID, intent, crew choices, run-route with receipt state (rule 16), settings, inputs in upload order; then the risk register with rescues (rules 4, 5, 10, 16).
7. **AFTER THE RESULT** — review in separate passes (identity → continuity → timing → camera → audio → style = every check of the project's Verify line, production-pipeline ch. 1); the binding take verdict order is post-audio-legal ch. 19 (hard rejects → rank survivors by emotion → repair the winner's local faults). The passes are run on what has actually been seen: if the result is not in front of you (no image/video in context, or a format you cannot view or hear), do not describe it — put the passes to the director as six questions in this exact order and record THEIR answers as the review, attributed ("director review, TK03"); a take whose review has not been recorded stays at its current status and is noted in the bible Handoff as `TKnn — review pending (director)`. On a fault, fix the weakest instruction in the NEXT prompt. On an approved take with a LOCAL fault, fix by scoped edit or extension where the model/surface offers one (Seedance 2.5 edit suite, rule 12; Runway Aleph Edit Studio; H3 V2V) — W5 routes the fault; a GLOBAL fault, or a model with no scoped edit route, goes back to the prompt: harvest the clean 2–4 s as coverage (production-pipeline ch. 10), fix the weakest instruction, regenerate. Counting: one bad roll = reroll; four bad rolls = failed iteration; 3 failed iterations = clean rewrite + channel change; 2 clean failures = model limit (rule 14).

## The Render Slate — delivery wrapper for every executable prompt

A director running several agents, sessions, platforms, and parallel renders cannot see from a bare code block what a prompt is for, where to run it, or what it needs. That context is operational information, not prompt prose — it goes in a compact **Render Slate**: a Markdown table immediately above the code block (key-value list where tables don't render). Use only applicable rows, in this order; omit unknown rows — no placeholders, no invented values. Adapt row labels to the user's output language; keep IDs and @tags ASCII-verbatim.

| Row | Content |
|---|---|
| `Render ID` | Collision-resistant ID of this exact prompt package: `<PROJECT>_<Shot ID>__<platform-model>__<operation>__P<nn>` (token rules below) |
| `Intent` | One director-readable line: shot, action, decisive creative constraint (starts with `Canon: DRAFT — …` when the treatment is not yet approved, rule 13) |
| `Crew choices` | One line: the craft-fillable decisions this prompt makes that the canon did not fix (light direction, lens/FOV, camera height, micro-cues) — the director's veto list (rule 13) |
| `Run in` | Route: platform → access route → project/workspace → surface/tool → model → mode as `id ("UI label")`, followed by the KEY and its receipt state (= rule 16) — never a route without version/snapshot and checked date. Example: `Higgsfield → web UI → project "Lighthouse" → Video → Seedance 2.5 → t2v (UI label unverified — read the live task dropdown) — from reference HF-WEB@2026-09-04 (checked 2026-09-04), not live-checked this session; confirm model/mode/workspace on the live form before Generate` |
| `Settings` | Executable UI values: ratio, resolution, duration, audio, any non-default control. Never repeat a setting inside a VIDEO prompt (no double control). Two documented exceptions: a control the project's A/B proved inert on this model — then that aspect goes into its prompt block and the UI setting stays Auto (platform-ui-workflows §1, blockquote "Do the controls bite?"); and the Higgsfield DoP tool (production-pipeline ch. 16). STILL prompts are different: the canvas/aspect/grid line is composition language for an image model and stays IN the prompt, first (style-control §2 "Layout before subject"), AND is set in the UI — that pairing is not double control |
| `Inputs` | One reference per line, numbered from 1 in slot/upload order: `n. @tag = what it is — its one job` (this row IS rule 5's attachment checklist; on a platform with a persistent library the same names are Elements and need no upload — say so). State whether the anchor goes in as a reference or as a literal start/end frame (rule 1). Mark `🟡 token form unverified — match the upload label before running` when the surface could not be seen (ch. 12b) |
| `Store in` | Known platform project/folder or local destination — omit rather than invent |
| `Handoff` | Only for linked work: extension boundary states, edit source + scope (`edit source …__T2V__P01__TK03`), or a continuity boundary |

**ID discipline:** the **Shot ID** is project canon from the shot board (`1A`, `SQ03_SC12_12A`) — never invent missing sequence/scene data. The **Render ID** appends platform/model, operation, and prompt-package revision (`…__HF-SD25__T2V__P01`; a rewrite is `P02`). A **Take ID** (`TK01`, `TK02`…) exists only once a generated result exists — never as a synonym for a prompt revision. Variant tokens only for deliberate creative alternatives, not reruns. A multi-shot take (rule 2) carries the Render ID of its FIRST internal shot; every internal shot's board row points to it (bible section B4 `Seq. take`).

**Tokens (fixed, ASCII, no dots — full grammar, instance chain and first-session bootstrap: production-bible 22e, read before writing a project's first Render ID):** `PROJECT` = the bible's title slug in CAPITALS (`LIGHTHOUSE`; no title yet → ask once, hold the row, never a placeholder). `platform-model` = ledger prefix (`HF`, `FAL`, `RW`, `OA`, `AR`, `CGPT`; `HF-CS4-…` via Cinema Studio) + model letters+digits with version (`SD25`, `SD20`, `NBP`, `GPTI2`, `SEEDR5`, `FLUX2`) — e.g. `HF-SD25`, `CGPT-GPTI2`. `operation` = `T2V` · `OMNI` · `EDIT` · `EXT` · `STILL` · `SHEET` · `PLATE` · `ANGLE` · `UPSCALE`. Asset prompts have no Shot ID: the @tag without `@` fills the slot (`LIGHTHOUSE_cat__HF-NBP__SHEET__P01`). Variant `_v<letter>` after the Shot ID only for a deliberate creative alternative; Take IDs (`__TK03`) only in the bible and review notes, never in a slate. Shot IDs without a shot board: `<scene><letter>` in delivery order (`1A, 1B … 2A`); the delivered shot table IS the shot board. A one-off prompt outside any project omits the Render ID row and says so.

**Filled instance:** worked-example.md §3 (complete slate + prompt + risk register); copy its row labels and value shapes.

## Workflow

1. **Intake** — resuming? Load the production bible first (ch. 22). New project: if a genre is named or evident, read `genre-baselines.md` first (it pre-answers defaults and tells you which files this project needs). The story comes from the user — run the story intake gate and offer a dramaturgical container (story-structures ch. 23) before craft settles. Then settle only what the conversation hasn't: format/look (stylized and UGC absorb errors; photoreal demands discipline; almost-photoreal is the uncanny danger zone) · target length & platform · deliverable (treatment/script/shot list/prompts) · model stack · dialogue language — decide the ROUTE now: (a) native in-model dialogue in the target language, (b) audio dub, (c) video dub with lip-sync (post-audio-legal ch. 18). Default is (a): write the language per the ch. 14 language pattern and prove it with one short draft-resolution test take (W3 step 5 settings) before building scenes; the skill does not list per-model language support, so treat it as unverified until that test passes or the live model page confirms it (rule 16 receipt). If the test fails, or the director wants a specific external voice: (b) for animation/off-camera, (c) for on-camera. Record language + route in the bible Frame section · then create the bible (W1 step 5).
   **Interaction contract.** Before the first deliverable, ask at most ONE message of questions, grouped: the story-gate gaps (23a) plus the intake items still open — nothing else. Everything the user has not answered is decided with a labeled default and shipped: craft per genre-baselines for the named genre; model stack per renderability §6 / production-pipeline ch. 5 for the declared look (name the pick); dialogue in the user's language. Every default is marked `ASSUMED` where it appears in the deliverable and logged in the bible decision log as `<date> — ASSUMED: <item> = <value> — confirm`. If the user says "just do it" or is unavailable (batch/subagent run), proceed on ASSUMED values; for canon-bound story gaps (rule 13) deliver both proposals in the deliverable, marked `PROPOSAL A/B — not canon`, instead of waiting. Follow-up questions after the first deliverable: one at a time, only when a canon-bound item blocks the next step.
2. **Write shot-first, canon-first** — when a treatment/script/bible exists, re-read its passage for the beat BEFORE writing (rule 13); when the treatment/shot list is itself the deliverable, author it as a DRAFT proposal from the intake (rule 13 scope) — ask only for story gaps (story-structures 23a), never per beat; canon-bound content (rule 13) the canon doesn't answer is settled with the director first, never improvised into the prompt. Then: numbered shots with fixed camera grammar per sequence, object-anchored blocking (never screen directions), @asset names, match-action cues. Sequence dramaturgy: Establish → Action → Reaction → Detail; dialogue as shot/reverse-shot with reverse plates + 180° lock (no recipe overrides this inside a take — recipe-level 360° cutting such as Ozu is edit-side only; strongest lock: the 3D blockout path, production-pipeline ch. 8).
3. **Lint** against renderability.md; rewrite or rescue every hit.
4. **Pre-production sections in the treatment** — set build (locations with locks + reverse decision), casting (sheet orders; for animation: expression sheets — order shape: production-pipeline ch. 3), style anchor = the project's style contract: one paragraph in the bible, derived from the recipe. It is never pasted as-is into a prompt. IMAGE prompts: it becomes the model's style section (GPT Image 2: [ART DIRECTION] per style-control §2; other stills per style-control §3–5). VIDEO prompts: it is distributed — light → LIGHTING, colour → COLOR GRADE/LOCATION, optics → OPTICS, acting → PERFORMANCE — and only its 4–8 load-bearing look tokens (style-control §6 meta rule) go verbatim into STYLE + POSITIVE LOCKS (ch. 12 placement rule 1).
5. **Deliver** per the routing table's file for the format — treatments end each scene with its shot table; its Shot IDs ARE the bible shot board's Shot IDs (assigned once here, never renumbered; the board = this table + status columns):
   `| Shot ID | Len | Framing | Action | Assets | Risk | Rescue |`
   `| 1A | 5 s | WS 63°, static, room corner | wet cat squeezes through the hatch, shakes, looks up at the dark lamp | @cat_wet @loc_lamproom | 🟡 paw manipulation | whole-body push |`
   Framing = shot size + FOV in degrees + camera move (ch. 12 vocabulary); Len = planned seconds inside the take; Assets = @tags only. Prompt shot lists follow rule 4 and rule 10 (artefact names: `references/glossary.md`). Close every work block by updating the production bible (rule 11; create it now if this block ordered assets and none exists).

This skill is maintained publicly (github.com/iret77/ai-film-production).
