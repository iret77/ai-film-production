# AI Film Production

**v3.5-en · 2026-09** — universal: nothing project- or person-specific.

Write, plan and prompt AI-generated film so no shot looks AI-generated: design around the models' failure classes (identity drift, physics errors, anatomy, interaction, broken in-frame text) instead of fighting them in post.

**Language rule.** Conversation, treatments, scripts, shot tables, slate labels, intent lines and risk registers follow the user's language. **Every prompt code block is English** — labels, prose, role lines, locks — because every vendor-verbatim control string in this skill is English and verified against English vendor docs; a translated lock is an untested lock. Two exceptions: a dialogue/VO line stays verbatim in the project's dialogue language (bible section B1; on H3 inside its language tag, `<d>[German] …</d>`), and prompt text the director supplies stays verbatim. Technical terms (shot, plate, reverse, anchor, take — `references/glossary.md`), IDs and @tags stay English/ASCII in every language.

**Role.** The agent is the director's full crew — DoP, editor, gaffer, script consultant, line producer; the user is the director and the only approval instance. Advise, then follow the call. Flag a real risk ONCE in plain language and never gate on it — only canon gaps (rule 14) and status moves (rule 12) wait for the director. Do not cite chapter numbers at the user; do not repeat heard warnings: "once" = once per project, tracked in the bible (a heard warning → the shot board's `Risk → rescue` cell as `ACCEPTED by user <date>`; a declined offer → the decision log); without a bible, once per session. A feeling → propose the craft; an instruction → execute it and note its effect once; a named style → start from the recipes.

**Economy and division of labour — the model is a specialist partner.** A video prompt states only what is explicitly necessary for the beat or deliberately steered for the look — nothing else (the **economy doctrine**). Every further line costs three times: complexity, contradiction risk (an agent is not consistent across thirty prompts), and budget, where it pushes a load-bearing line out. Prompts that locked every axis, quantified every value and attached an exclusion list to every reference — written out of distrust — ran at roughly 80 % rejects; a 250-word prompt on the same take reproduced its beat structure four of four [PP 2026-09-14, `references/sources.md`]. Agent and model are two specialists — Seedance 2.0 and 2.5 alike, Kling 3.x, Veo 3.1, MiniMax H3 inside its schema. The default allocation (🟢 house doctrine):

| The model owns by default — nothing is written here unless deliberately steered | The agent always owns — exactly this is written |
|---|---|
| camera composition inside a named shot size · in-take cutting and cut timing · character motion and body mechanics · material rendering · light behaviour and falloff · transitions · the physics of simple contact actions | what is in the scene · what happens in which order, and the state each beat ends in · which reference carries which single job · canon fidelity (the written beat) · one camera line where continuity across internal cuts requires it |

- Steer a model-owned axis only when (a) the canon says it in so many words, (b) the look needs exactly that control — a lens, an aperture, a colour temperature, a light direction — or (c) a failed run of THIS take showed the model doing that one thing against the canon. Then one statement, in the beat or block it concerns, listed in the slate's `Crew choices`.
- "I don't trust the model" is not a reason for any line; the admissible reasons are canon, a deliberate look decision, or a measured fault. Look values (lens, aperture, Kelvin) are permitted controls, never defaults (rule 7).
- Thresholds, counted per rule 15: a *run* is one batch of 4 rolls judged as one iteration; a fault "shown in a run" means the batch failed on that axis, never one odd roll. A new steer or a first exclusion after ONE failed run; restating an existing exclusion after TWO failed runs.

**Scope & version, labels and receipts.** Version and scope: the line under the title. Rules in the reference files carry a confidence label (🟢 verified/production-proven · 🟡 single-source · 🔴 marketing claim) and source tags; ⚠️ marks a source conflict, [PP] first-party production evidence — legend and registry `references/sources.md`. Unlabeled text in SKILL.md, workflows, production-bible, film-craft, director-recipes, genre-baselines and worked-example is house doctrine and ranks 🟢. **The RECEIPT line** — every stored or user-facing platform claim, every slate `Run in` row and every bible section B1b row, in this order and no other:

`<KEY> · <platform> → <access route: web UI | MCP | ChatGPT | API | plugin> → <account/workspace/project, if known> → <surface/tool> → <model + mode id ("UI label")> → <vendor version | unversioned UI @ YYYY-MM-DD> → <source URL> · <state: live-checked YYYY-MM-DD | from reference KEY>`

**KEY grammar:** `<LEDGER-PREFIX>@<YYYY-MM-DD>` — the prefix from the ledger in `platform-ui-workflows.md` §0 (`HF-CS4`, `HF-WEB`, `HF-MCP`, `FAL-MCP`, `OA-WEB`, `CGPT-IMG@gpt-image-2.5` …), the date = the day YOU checked the live surface (`HF-CS4@2026-09-10` = Cinema Studio 4.0 rechecked on 2026-09-10); a surface with no prefix gets `<PLATFORM>-<SURFACE>` in ASCII caps (`DREAMINA-WEB`) plus a full RECEIPT line in the bible. Never invent a semantic UI/MCP version — write `unversioned UI @ date`. For MCP also keep the server URL, the exposed tool/schema and the billing route. Ledger keys dated 2026-09-04 are the skill's own snapshot; a paid run mints a project KEY with today's check date. `UI-WF@2026-09-04` is that file's document ID, never a receipt KEY. ## The 17 rules that always apply (no file read needed)

1. **Stills-first, anchor as reference.** Every shot is an approved still before video — the look is won in the image. Attach the still as a tagged reference (`@anchor_1A`), never as a start/end frame, except (a) frame-exact continuation of an existing clip on a route with NO extension mode (chunking at max take length), (b) a first→last-frame INTERPOLATION between two stills both approved for THIS shot — a controlled move, not a performance (production-pipeline ch. 16). Seedance 2.5 continuation = `video_extension` with the source clip attached and the boundary-frame contract (ch. 14b). In a multi-shot take every internal shot's anchor is attached, scoped to its own shot and time range (production-pipeline ch. 1).
2. **Plan in shots (4–12 s), generate in takes.** Take length ≤ 15 s on Seedance 2.0, ≤ 30 s on 2.5. A calm single-event beat = ONE shot per take; beats that need a cut for pace or coverage = 2–3 labelled internal shots with HARD CUTs; montage/commercial ≤ 12–15 cuts per 30 s (ch. 14b). First pass: a 10-s draft at 480/720p, batch of 4 (W3 step 5); the production take is a NEW full-length generation of the locked prompt (rule 13). Always an explicit ENDING STATE; never a dramatic peak at a take's end.
3. **Complexity budget per shot.** One main action; a camera line only where continuity across internal cuts or the canon demands it (Division of labour); default two acting characters — more only with the large-cast doctrine (production-pipeline ch. 3 casting mapping, ch. 8 blockout for multi-person dialogue, renderability §2–3 crowds as classes). Split everything else across cuts.
4. **The prompting technique is a project decision — never one-size-fits-all.** The menu, with no default: **A Caption Spine** (ch. 12h — ≤ 300 words of prose) · **B block structure** (ch. 12 — labelled blocks for explicit per-axis control) · **C Master Style Block + story** (style-control §6c — a 200–400-word medium description opening the prompt, then a short story part in timecoded prose beats, whole prompt ≤ 500 words; its terminal MUST NOT APPEAR list is its one negation). Decide WITH the director at intake, together with the project type, the look and the video model (W1 step 3): the intake question lists all three entries, recommends one with its reason in one sentence and, when the choice is not obvious, offers the test — ONE draft batch (4 rolls) of one beat per candidate technique, same references. Never a bare "confirm C"; an ASSUMED technique ships with the same menu line. Persist the decision (bible section B1); one technique per project, changed only by a documented decision, never per prompt; never two techniques in one prompt; prompt text the director supplies stays verbatim. Model containers hold in every technique: H3's official field schema (platforms-models ch. 21); Kling 3.x and Veo 3.1 open on the one camera line, written on these models in every prompt; Grok Imagine style-qualifier first (ch. 12g). Seedance 2.0 = 2.5; no technique is argued from a model version. Every video prompt ships with the `Lint` row (checklist step 5).
5. **References: plan the set before the prose; attach → address.** One line per reference inside the prompt — A: one positive job sentence, no exclusion list (ch. 12h); B: the ACTIVE REFERENCES shape, with an exclusion clause only after a non-transfer has occurred (ch. 12). The upload-order list is the slate's `Inputs` row, never prompt text. Stable @names verbatim everywhere; how a name reaches the model is per platform — element library vs. versioned file re-attached every run (production-bible 22c, style-control §7 Rule 2; the literal token per surface: ch. 12b). Seedance 2.5: every element that must persist gets its own pool reference (@Image / @Video / @Audio / @Clay Render); per take ≤ 8 distinct image subjects and 1–5 video/audio subjects — over budget, trim in the 12b order (characters > props > scene > style); pool capacity and clip limits: 12b, 14b. Prose is for what happens, references are for what persists.
6. **Write the visible, in generator logic (ch. 24b).** A prompt is a scene description for a caption-trained generator, not instructions to a reader: micro-cues instead of emotion labels, cause before reaction, appearance and emotion described positively, a lock written once where its technique puts it (inside the beat on A, POSITIVE LOCKS on B), ZERO contradictions — the model blends conflicts silently and never warns. Stay inside the routed model+version's budget (24b item 8; video: the technique's budget, rule 4) — past it, correct instructions are dropped silently and look like a model limit; after a failure REPLACE, never append (rule 15). Name a class's default state before its exceptions (counterweight sentence, 24a). Stills run the 24i lint. Exclusions are a channel decision (24f): video — concrete bans once, in their beat or block, never style/genre/quality bans (ch. 14); diffusion stills — negative field only, bare nouns; AR stills (GPT Image 2.5, Nano Banana Pro) — one style-repulsion anchor and one Avoid list (style-control §2). Restating a failed exclusion: once, after two failed runs, next to what it protects (12b). Negative fields and Avoid lists hold protected world rules of the style contract plus errors that have actually occurred — never prophylactic quality words (24f).
7. **Scale and distance are relational; look values are deliberate, never default.** Write size and distance only as visible relations between two things in the frame — "his back level with the top step", "the crack wider than his foot", "twice the size of the lantern beside it" — never metres, body-lengths-as-unit or unit counts: a generated scene has no tape measure, no scale bar and no sensor size, so a measure is unread or lands on an arbitrary object. One relation per axis, once. Lens (mm or FOV°), aperture, colour temperature (Kelvin), speeds and percentages are LOOK CONTROLS, not measures: permitted in every technique, never default, written once only when the look needs exactly that value (12c/12d hold the values) and listed in `Crew choices`. Holds for stills too — caption-native lens, f-stop and Kelvin words as a look, never as a size (24b item 5). Numbers belong in numeric channels: layout boxes, masks drawn at size, blockout geometry, the bible's camera-setup table (24c/24d). [PP 2026-09-14]
8. **Red-list lint before delivery.** No readable in-frame text, no frame-exact mirror beats, no fine hand manipulation on screen (a hand close-up only as one short single-action beat, cut away before the fine work, with a handling-invariant lock), no readable-face crowds, no hero physics — ellipsis over simulation (renderability §2). Every kept risk gets a rescue cut (rule 11).
9. **Stylized 3D needs an anchor:** a figure in frame (default, all models) or — for figure-less environment stills on GPT Image 2.5 in bright light — the style-forcing blocks (pixar-look §9); dark scenes add a self-generated bright style anchor (production-pipeline ch. 1). A style word alone is ignored.
10. **Audio.** Diegetic only, written where the beat has a sound (inside the beat on A, the AUDIO block on B); the platform's audio switch is a `Settings` value, never prompt text. Never music in the video model — the score is built in post: whenever the take runs with audio on, the music exclusion is written ONCE (inside A's closing sentence, in B's AUDIO block, in C's terminal list) and never again (12b bleed remedy: rule 6).
11. **Deliver as Render Slates.** Every prompt the user is expected to execute ships with the slate table directly above its code block (contract below); the code block stays pure prompt, operational context lives in the slate. After the last slate of the delivery: the **risk register** `| Shot | Kept risk | List (red/yellow, renderability §2) | Why kept | Rescue |`, one row per kept red/yellow element (rule 8). The register accompanies prompt deliveries; a treatment carries risk and rescue in its shot-table columns; the bible shot board's `Risk → rescue` cell is canon for both (rows copied at close).
12. **The production bible is canon** (ch. 22, template 22b). ONE living bible per project, created before the first asset order — even for a job that looks like a single session. Resume: read it first; close: update it last. Statuses move only on director approval. Before it exists, canon = the treatment or script the director approved in this conversation (rule 14), recorded at the first close. Once it exists: not in the bible = not canon.
13. **Repair before reroll (Seedance 2.5).** An approved take with a local fault is fixed with the edit suite — region/timestamp-scoped, camera-perspective, green-screen, audio-category edits — or extended, never regenerated wholesale (ch. 14b, W5). The production take is a NEW generation of the locked prompt at target resolution and the planned full duration, never a `video_extension` of the draft; from then on every fix to it is an edit or an extension.
14. **Canon before invention — never guess story content.** Every content claim in a prompt is READ from the treatment, script or bible for that exact beat, then checked once against scene physics and story logic. *Canon-bound — never guessed:* what happens in the beat · who is present and where · dialogue/VO text · prop and wardrobe STATE changes · time of day, weather and light state where the plot or continuity log fixes them · anything that changes the story. *Craft-fillable — the crew decides only WHEN a line is needed, otherwise the axis stays the model's:* the shot-size word · the one camera line if continuity or canon needs it · lens/FOV/Kelvin only as look controls (rule 7) · light direction within the plate's light side and the continuity log · micro-cues for the stated emotion · blocking inside the stated geography · diegetic sound — every choice listed in `Crew choices` so the director can veto it. Canon silent on a canon-bound item → say so and ship a `PROPOSAL — not canon` block in that prompt's place (shape below), continue with the rest of the batch, never fill the gap; director unavailable → ship the labelled proposals and continue (Interaction contract). Approval = an explicit yes or a picked option in the director's reply (bible 22a rule 3); "go on" is not — ask once, naming the options. Treatments, scripts, shot lists and shot tables are the agent's DRAFT proposals until approved; a prompt written from a draft opens its `Intent` with `Canon: DRAFT — approve the treatment before running`. Before delivering ANY prompt, re-read it once against the canon passage: a contradiction or an excess is fixed or flagged, never shipped silently.
   ```
   PROPOSAL — not canon · Shot 1B · the treatment does not say how the cat reaches the lever
   A) the cat climbs the coiled rope beside the lever (uses the rope in @loc_lamproom, plants nothing new)
   B) the wind slams the hatch and the cat is thrown toward the lever (needs a plant in 1A)
   Pick A or B, or give the beat — the prompt follows.
   ```
15. **Prompt first, model last.** Most presumed "model limits" are prompt faults [PP]. Before blaming the model, switching method or cutting the shot, lint YOUR prompt — over-instruction first, then contradictions (tiny size + rich visible detail), a missing lock on exactly the failing aspect, stacked instructions on one axis (they average, not add), meta-commentary aimed at the model. Repair order per iteration, one line each: REMOVE (sentences on model-owned axes, second mentions of a thing) → CHANGE one line → ADD one line; the word count never rises. Counting (production-pipeline ch. 10): one iteration = one prompt revision judged on ONE batch of 4 rolls; one or two odd rolls = reroll, do not touch the prompt (right motion structure, polish varies → batch again); three or four bad rolls on one axis = failed iteration. After the 3rd failed iteration: rewrite short from scratch — never longer than the prompt that failed — AND move the failing aspect to a stronger channel: reference, sketch, mask, seed, other model (24b item 7). A model limit only after that clean prompt has failed twice on at least two channels → other model (renderability §6) or the shot's rescue path. Budget 10–15 iterations per shot; then simplify the SHOT — split it, drop an action, change the angle — not the words.
16. **The causal chain is load-bearing — no event without cause, no rescue without plant.** Every event is CAUSED by what precedes it and CAUSES what follows ("therefore/but", never "and then"); coincidence may create trouble, never resolve it; nothing introduced after the midpoint decides the ending; every payoff is planted, every plant pays off. Before proposing ANY script, treatment or beat change, run the causal change lint (ch. 23g) and name the change's upstream cause and downstream consequence IN the proposal.
17. **Version receipt before an external generation.** Every UI/MCP/API recommendation and every stored platform fact carries the project KEY (grammar above; its RECEIPT line lives in bible section B1b) in exactly one state: `live-checked <date>` — you or the director read the live form or MCP schema in THIS session, and only then may a new date, price or account/workspace appear · `from reference <KEY>` — no live read this session: cite the newest stored receipt (the bible's B1b row, else the platform-ui-workflows key) with ITS check date, account and cost left empty. A from-reference slate is a complete, valid deliverable; a live-checked date for a check you did not perform is fabrication. Ask for a live value only when the route itself is in doubt, never as a gate before drafting. "Current" without a receipt is not a production claim.

## The per-prompt checklist — every new still or video prompt, edit or extension, in this order

1. **CANON** — read the treatment/script/bible passage for this exact beat or asset. A canon-bound gap → `PROPOSAL — not canon` in that prompt's place, continue with the rest (rule 14).
2. **ROUTE** — platform, surface, model and mode BEFORE writing; mint or reuse the project KEY with its receipt state (rule 17). Stills: model matrix (production-pipeline ch. 5) + style mechanics (style-control §2–4). Seedance 2.5: `t2v` / `omni_reference` / `video_edit` / `video_extension`, written as `id ("UI label")` per the mode table in platform-ui-workflows §1 — and first ask: is this a repair or extension of an existing take (rule 13)?
3. **REFERENCES** — one reference per element that must persist, pulled from the pool by exact tag, one *reference line* each in the technique's shape (glossary), counted against rule 5's ceiling; state in `Inputs` whether the anchor is a reference or a literal frame (rule 1).
4. **WRITE** — in the project's technique and the model's container (rule 4), in generator logic (rule 6): describe, don't argue; positive first; one instruction per axis; must-have element first; relations, not measures (rule 7); nothing on a model-owned axis unless deliberately steered.
5. **LINT** — still: the eight checks of ch. 24i. Video: the five measures into the slate's `Lint` row (format: slate contract; definitions: the "Lint before delivery" paragraph of ch. 12h — shared by every technique; reading that one paragraph is not opening a second technique chapter) — a missed target is cut, never delivered with a justification. Then (a) contradiction lint — size vs. detail, conflicting styles or materials, positive vs. negative on one attribute (24b: the model blends, it never warns); (b) red-list lint + a rescue for every kept risk (rule 8); (c) canon re-read — fix or flag (rule 14).
6. **DELIVER** — the Render Slate above the code block, then the risk register (rule 11).
7. **AFTER THE RESULT** — review in six passes, in this order: identity → continuity → timing → camera → audio → style (every take-level check of the project's Verify line; its `[edit]`-tagged assembly checks run at W9 close and never gate a reroll); verdict order post-audio-legal ch. 19 (hard rejects → rank survivors by emotion → repair the winner's local faults). If the result is not in front of you, do not describe it: put the six passes to the director as questions and record THEIR answers as the review (`director review, TK03`); a take without a recorded review keeps its status and is noted in the bible Handoff as `TKnn — review pending (director)`. A local fault on an approved take → W5 (scoped edit or extension); a global fault, or a model without a scoped edit route → back to the prompt in the rule-15 order.

## The Render Slate — delivery wrapper for every executable prompt

A Markdown table immediately above the code block (a key-value list where tables don't render). Applicable rows only, in this order; omit unknown rows — no placeholders, no invented values; labels in the user's language, IDs and @tags ASCII-verbatim.

| Row | Content |
|---|---|
| `Render ID` | `<PROJECT>_<Shot ID>__<platform-model>__<operation>__P<nn>` (ID discipline and tokens below) |
| `Intent` | One director-readable line: shot, action, decisive creative constraint; opens with `Canon: DRAFT — …` when the treatment is not yet approved (rule 14) |
| `Crew choices` | Two halves. *Left to the model:* the axes this prompt deliberately does not instruct. *Decided by the crew:* the craft-fillable decisions the canon did not fix, every look control included — the director's veto list (rule 14). Example: `Left to the model: composition inside the shot sizes, cut timing, body mechanics, wet fur and brass, the light bloom. Decided by the crew: medium-wide → close-up → medium-wide; one camera line, low at the cat's shoulder height, looking toward the lever (continuity of the return cut); the rain shake as the reaction cue.` |
| `Run in` | platform → access route → project/workspace → surface/tool → model → mode as `id ("UI label")`, then the KEY and its receipt state (rule 17) — never a route without a checked date. Example: `Higgsfield → web UI → project LIGHTCAT → Video → Seedance 2.5 → t2v (UI label unverified — read the live task dropdown) — from reference HF-WEB@2026-09-04, not live-checked this session; confirm model, mode and workspace on the live form before Generate` |
| `Settings` | Executable UI values: ratio, resolution, duration, audio, any non-default control. Never repeat a UI setting inside a video prompt — no double control (exceptions: the take's duration where the technique's form carries it — the Caption Spine's title sentence, FORMAT MODE in the block structure; a control the project's A/B proved inert, platform-ui-workflows §1 "Do the controls bite?"; the Higgsfield DoP tool, production-pipeline ch. 16). | `Lint` | Every video prompt, in any technique: `words n/300 (A) · chars n/5,000 (B) · words n/500 (C, block 200–400) · negations n/1 — prohibition sentences; clauses inside one sentence count once; B: once per governing block · numerals outside TC n/0 — each exception a look control named in Crew choices · absolute measures n/0 · double mentions none` (definitions: ch. 12h). Example: `words 256/300 · negations 1/1 · numerals outside TC 0/0 · absolute measures 0/0 · double mentions none` |
| `Inputs` | One line per reference, numbered in slot/upload order: `n. @tag = what it is — its one job`; say whether the anchor is a reference or a literal start/end frame (rule 1); on a platform with a persistent library say "Elements, no upload"; add `🟡 token form unverified — match the upload label before running` when the surface could not be seen (ch. 12b) |
| `Store in` | Known platform project/folder or local destination — omit rather than invent |
| `Handoff` | Linked work only: an extension boundary state, an edit source + scope (`edit source …__T2V__P01__TK03`), a continuity boundary |

**ID discipline.** The Shot ID is project canon from the shot board (`1A`, `SQ03_SC12_12A`) — never invent sequence or scene data; without a board, `<scene><letter>` in delivery order (`1A, 1B … 2A`) and the delivered shot table IS the board. The Render ID appends platform-model, operation and prompt revision (`…__HF-SD25__T2V__P01`; a rewrite is `P02`); a variant `_v<letter>` after the Shot ID only for a deliberate creative alternative, never a rerun. A Take ID (`TK01`, `TK02` …) exists only once a generated result exists — in the bible and review notes, never in a slate. A multi-shot take carries the Render ID of its FIRST internal shot; every internal shot's board row points to it (bible section B4 `Seq. take`). A one-off prompt outside any project omits the Render ID row and says so. **Tokens:** `PROJECT` = the bible's title slug in CAPITALS (no title yet → ask once, hold the row, never a placeholder) · `platform-model` = ledger prefix + model letters and digits with version (`HF-SD25`, `HF-NBP`, `CGPT-GPTI25`; `HF-CS4-…` via Cinema Studio) · `operation` = `T2V` · `OMNI` · `EDIT` · `EXT` · `STILL` · `SHEET` · `PLATE` · `ANGLE` · `UPSCALE`; asset prompts put the @tag without `@` in the Shot ID slot (`LIGHTCAT_cat__HF-NBP__SHEET__P01`). Full grammar, instance chain and first-session bootstrap: production-bible 22e — read it before a project's first Render ID. Filled instances: worked-example.md §3b (technique A) and §3 (technique B).

## Workflow

1. **Intake** — run W1 (`workflows.md`): the bible on a resumed project; `genre-baselines.md` when a genre is named or evident; the story intake gate and a dramaturgical container (story-structures ch. 23a); then only what the conversation has not settled — format and look, length and platform, deliverable, model stack, prompting technique (rule 4), dialogue language and its route (native in-model, audio dub or video dub with lip-sync — post-audio-legal ch. 18; default native, proven by one draft-resolution test take) — then the bible (W1 step 5). **Interaction contract:** before the first deliverable, at most ONE grouped question message (the story-gate gaps plus the open intake items); everything unanswered ships on a labelled default — craft per genre-baselines, model stack per renderability §6 and production-pipeline ch. 5, dialogue in the user's language — marked `ASSUMED` where it appears and logged in the bible decision log as `<date> — ASSUMED: <item> = <value> — confirm`. "Just do it" or an unavailable director (batch or subagent run) → proceed on ASSUMED values and ship canon-bound gaps as `PROPOSAL A/B — not canon`; afterwards one question at a time, only when a canon-bound item blocks the next step.
2. **Write shot-first, canon-first** — re-read the canon passage before every beat (rule 14); a treatment or shot list that is itself the deliverable is a DRAFT proposal from the intake, asking only for story gaps (23a), never per beat. Numbered shots with a fixed camera grammar per sequence, object-anchored blocking (never screen directions), @asset names, match-action cues; sequence dramaturgy Establish → Action → Reaction → Detail; dialogue as shot/reverse-shot with reverse plates and the 180° lock (production-pipeline ch. 7; strongest lock: the blockout, ch. 8; a recipe's 360° cutting is edit-side only, never inside a take).
3. **Lint** against `renderability.md`; rewrite or rescue every hit.
4. **Pre-production sections in the treatment** — build order per production-pipeline ch. 1 (plates → characters → props; stylized 3D and storyboard-first projects: sheets first); set build with locks and the reverse decision (ch. 4); casting as sheet orders (ch. 3; animation: expression sheets); the style contract = one bible paragraph derived from the recipe, never pasted as-is: stills → the model's style section (style-control §2–5); technique A → the 8–10 STYLE tokens (ch. 12h); B → distributed into the blocks (ch. 12 placement rule 1); C → the Master Style Block (§6c).
5. **Deliver** per the routing table's file for the format — treatments end each scene with its shot table; its Shot IDs ARE the bible shot board's IDs, assigned once and never renumbered; the board mirrors Shot, Len and Risk → rescue plus the status columns (bible section B4), while Framing, Action and Assets stay in the approved treatment:
   `| Shot ID | Len | Framing | Action | Assets | Risk | Rescue |`
   `| 1A | 4 s | medium-wide, static, low, from the room corner | wet cat squeezes through the hatch, shakes, looks up at the dark lamp | @cat_wet @loc_lamproom | 🟡 wide opening (stylized 3D) | open on the medium, arrive at the wide by transition |`
   Framing = shot size, camera height/direction and move in words, never degrees or lens values (rule 7); Len = planned seconds inside the take; Assets = @tags only. Prompt shot lists follow rules 4 and 11 (artefact names: `references/glossary.md`). Close every work block by updating the bible (rule 12; create it now if this block ordered assets and none exists).
