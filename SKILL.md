# AI Film Production

**v3.4 · 2026-09** — universal: nothing project- or person-specific.

Write, plan and prompt AI-generated film so no shot looks AI-generated: design around the models' failure classes (identity drift, physics errors, anatomy, interaction, broken in-frame text) instead of fighting them in post.

**Language rule.** Conversation, treatments, scripts, shot tables, slate labels, intent lines and risk registers follow the user's language. **Every prompt code block is English** — every vendor-verbatim control string is English; a translated lock is an untested lock. Two exceptions: a dialogue/VO line stays verbatim in the project's dialogue language (bible section B1; on H3 inside its language tag, `<d>[Japanese] …</d>`), and prompt text the director supplies stays verbatim. Technical terms (`references/glossary.md`), IDs and @tags stay English/ASCII.

**Role.** The agent is the director's full crew — DoP, editor, gaffer, script consultant, line producer; the user is the director and the only approval instance. Advise, then follow the call.
- Flag a real risk ONCE per project, in plain language, and never gate on it — only canon gaps (rule 14) and status moves (rule 12) wait for the director. Never cite chapter numbers at the user.
- A heard warning goes into the bible shot board's `Risk → rescue` cell as `ACCEPTED by user <date>`, a declined offer into the decision log; without a bible, once per session.
- A feeling → propose the craft; an instruction → execute it and note its effect once; a named style → start from the recipes.

**Economy and division of labour — the model is a specialist partner.** A video prompt states only what is explicitly necessary for the beat or deliberately steered for the look (the **economy doctrine**). Every further line costs three times: complexity, contradiction risk (an agent is not consistent across thirty prompts), and budget, where it pushes a load-bearing line out. Prompts that locked every axis, quantified every value and hung an exclusion list on every reference ran at roughly 80 % rejects; a 250-word prompt on the same take reproduced its beat structure four of four [PP 2026-09-14, `references/sources.md`]. The rejects were prompt faults, not render faults: contradictions inside the prompt, technical instead of scenic description, absolute sizes without a scale, missing acting directions, inconsistent timing and geography, metaphors that pull off-theme, working lines dropped between revisions. Length is not limited — a prompt that states what belongs in it, once, limits itself (ch. 12h). The default allocation (🟢 house doctrine, every video model):

| The model owns by default — nothing is written here unless deliberately steered | The agent always owns — exactly this is written |
|---|---|
| camera composition inside a named shot size · in-take cutting and cut timing · character motion and body mechanics · material rendering · light behaviour and falloff · transitions · the physics of simple contact actions | what is in the scene · what happens in which order, and the state each beat ends in · which reference carries which single job · canon fidelity (the written beat) · one camera line where continuity across internal cuts requires it |

- Steer a model-owned axis only when (a) the canon says it in so many words, (b) the look needs exactly that control — a lens, an aperture, a colour temperature, a light direction — or (c) a failed run of THIS take showed the model doing that one thing against the canon. Then one statement, in the beat or block it concerns, listed in the slate's `Crew choices`.
- "I don't trust the model" is not a reason for any line.
- A *run* is one batch of 4 rolls judged as one iteration (rule 15); a fault "shown in a run" means the batch failed on that axis, never one odd roll. A new steer or a first exclusion after ONE failed run; restating an existing exclusion after TWO.

**Scope & version.** Reference rules carry a confidence label (🟢 verified/production-proven · 🟡 single-source · 🔴 marketing claim), source tags, ⚠️ for a source conflict and [PP] for first-party production evidence — legend, source tiers and registry: `references/sources.md`. Unlabeled text in SKILL.md, workflows, production-bible, film-craft, director-recipes, genre-baselines and worked-example is house doctrine and ranks 🟢. **The RECEIPT line** — every stored or user-facing platform claim, every slate `Run in` row and every bible section B1b row, in this order:

`<KEY> · <platform> → <access route: web UI | MCP | ChatGPT | API | plugin> → <account/workspace/project, if known> → <surface/tool> → <model + mode id ("UI label")> → <vendor version | unversioned UI @ YYYY-MM-DD> → <source URL> · <state: live-checked YYYY-MM-DD | from reference KEY>`

`KEY` = `<LEDGER-PREFIX>@<the day YOU checked the live surface>` (`HF-WEB@2026-09-10`); prefixes and the full KEY grammar: `platform-ui-workflows.md` §0. Receipt states: rule 17.

## Precedence — when two instructions collide

1. An explicit director instruction wins (Role).
2. Project canon (bible → approved script → approved treatment) beats any skill default.
3. The always-rules beat reference-file text — EXCEPT where a reference chapter names the rule it narrows ("Reconciled with SKILL rule N", "exception to SKILL rule N"); such an exception applies inside its stated scope only.
4. Reference chapters beat examples and templates (worked-example.md, the 22b template) where they differ.
5. Between two reference rules: (a) a ⚠️-marked conflict is settled by the sentence next to the marker; (b) a rule scoped to the model, platform or scenario at hand beats a general rule — a technique chapter beats ch. 12g for a named model; (c) otherwise 🟢 outranks 🟡 outranks 🔴, and at equal label the source tier decides (sources.md legend): vendor documentation and first-party measurement [PP] > platform tutorials and established practitioners > single social finds, which never win a frontal contradiction with a vendor statement without striking proof. A rule learned on an older model version holds on the newer one until version-specific information says otherwise.
6. Routing table, always-rules, per-prompt checklist and Workflow are cumulative layers (what to read → constraints → order of work → order of deliverables), not competitors.

Still open after this ladder → name both rules to the director in one line and ask.

## The 17 rules that always apply (no file read needed)

1. **Stills-first, anchor as reference.** Every shot is an approved still before video — the look is won in the image. Attach the still as a tagged reference (`@anchor_1A`), never as a start/end frame; a multi-shot take attaches every internal shot's anchor, scoped to its own shot and time range (production-pipeline ch. 1).
   - A literal frame only for a frame-exact join on a route with NO extension mode, or a first→last-frame INTERPOLATION between two stills approved for THIS shot — a controlled move, not a performance.
   - Seedance 2.5 continues with `video_extension` from the source clip (ch. 14b).
2. **Plan in shots (4–12 s), generate in takes.** Take length ≤ 15 s on Seedance 2.0, ≤ 30 s on 2.5; always an explicit ENDING STATE, never a dramatic peak at a take's end.
   - A calm single-event beat = ONE shot per take; beats that need a cut for pace or coverage = 2–3 labelled internal shots with HARD CUTs; montage/commercial ≤ 12–15 cuts per 30 s (ch. 14b).
   - First pass: a draft batch of 4 at 480/720p in the take's planned length (10 s when nothing else is planned; W3 step 5); the production take: rule 13.
3. **Complexity budget per shot.** One main action; default two acting characters — more only with the large-cast doctrine (production-pipeline ch. 3 and ch. 8, renderability §2–3); a camera line only where continuity across internal cuts or the canon demands it. Split everything else across cuts.
4. **The prompting technique is a project decision — never one-size-fits-all.** The menu, with no default: **A Caption Spine** (ch. 12h — a caption in prose) · **B block structure** (ch. 12 — labelled blocks, explicit per-axis control) · **C Master Style Block + story** (style-control §6c — a seven-layer medium description, then a short story part in prose beats; its terminal MUST NOT APPEAR list is its one negation).
   - Decide WITH the director at intake, together with project type, look and video model (W1 step 3): the question lists all three entries, recommends one with its reason in one sentence and, when the choice is not obvious, offers the test — ONE draft batch (4 rolls) of one beat per candidate, same references. Never a bare "confirm C"; an ASSUMED technique ships with the same menu line.
   - Persist the decision in bible section B1: one technique per project, changed only by a documented decision, never per prompt, never two in one prompt.
   - Model containers hold in every technique (ch. 12g, ch. 21): H3's official field schema; Veo 3.1 opens on the one camera line (Google's formula); camera-first on Kling 3.x and a leading style qualifier on Grok Imagine are 🟡 recommendations. Seedance 2.0 know-how holds on 2.5 unless a documented difference says otherwise (ch. 14b table): timecode beats are a 2.5 form, on 2.0 the beats are numbered shots.
5. **References: plan the set before the prose; attach → address.** Prose is for what happens, references are for what persists.
   - One line per reference inside the prompt, one job each — A: one positive job sentence, no exclusion list (ch. 12h); B: the ACTIVE REFERENCES shape, an exclusion clause only after a non-transfer has occurred (ch. 12). A reference used only IN PART names its part positively; a video or audio reference used in part also names what is not taken, from the first run — a scoping clause, not a negation.
   - Stable @names verbatim everywhere; the literal token per surface: ch. 12b. The upload-order list is the slate's `Inputs` row, never prompt text.
   - Seedance 2.5: every element that must persist gets its own pool reference; per take ≤ 8 distinct image subjects and 1–5 video/audio subjects (trim order when over budget: ch. 12b).
6. **Write the visible, in generator logic (ch. 24b).** A prompt is a scene description for a caption-trained generator, not instructions to a reader.
   - Micro-cues instead of emotion labels; cause before reaction; appearance and emotion positive; a class's default state before its exceptions (24a); each lock once, where its technique puts it; ZERO contradictions — the model blends conflicts silently and never warns.
   - Length: a still prompt stays inside the routed model+version's measured word budget (24b item 8) — past it, correct instructions are dropped silently. A video prompt has no house word ceiling (a vendor-documented target stays — H3 Ref2VA, ch. 21): it states what belongs, once, and stops when complete (ch. 12h, the eight checks). After a failure REPLACE, never append.
   - Exclusions are a channel decision (24f). Video: a concrete ban once, in its beat or block; a style/genre/quality ban only as technique C's single terminal list — A and B carry the look positively (evidence and condition: ch. 14). Diffusion stills: negative field only, bare nouns. AR stills (GPT Image 2.5, Nano Banana Pro): one style-repulsion anchor and one Avoid list (style-control §2). A list holds protected world rules plus errors that actually occurred, never prophylactic quality words; a failed exclusion is restated once, after two failed runs, next to what it protects (ch. 12b).
7. **Scale and distance are relational; look values are deliberate, never default.**
   - Write size and distance only as visible relations between two things in the frame — "his back level with the top step", "twice the size of the lantern beside it" — never metres or unit counts: a generated scene has no tape measure, so a measure is unread or lands on an arbitrary object. One relation per axis, once. [PP 2026-09-14]
   - Lens (mm or FOV°), aperture, colour temperature (Kelvin), speeds and percentages are LOOK CONTROLS: permitted in every technique, never default, written once only when the look needs exactly that value (values: 12c/12d; stills: 24b item 5) and listed in `Crew choices`.
   - Numbers belong in numeric channels: layout boxes, masks drawn at size, blockout geometry, the bible's camera-setup table (24c/24d).
8. **Red-list lint before delivery.** No readable in-frame text, no frame-exact mirror beats, no fine hand manipulation on screen (a hand close-up only as one short single-action beat, cut away before the fine work, with a handling-invariant lock), no readable-face crowds, no hero physics — ellipsis over simulation (renderability §2). Every kept risk gets a rescue cut (rule 11).
9. **Stylized 3D needs an anchor:** a figure in frame (default, all models) or — for figure-less environment stills on GPT Image 2.5 in bright light — the style-forcing blocks (pixar-look §9); dark scenes add a self-generated bright style anchor (production-pipeline ch. 1). A style word alone is ignored.
10. **Audio — diegetic only; the score is built in post.** Sound is written where the beat has it (inside the beat on A, the AUDIO block on B), in ONE audio notation (ch. 12b); the platform's audio switch is a `Settings` value, never prompt text. Never music in the video model: whenever the take runs with audio on, the music exclusion is written ONCE as a plain sentence (A's closing sentence, B's AUDIO block, C's terminal list) and never again (12b bleed remedy: rule 6).
11. **Deliver as Render Slates.** Every prompt the user is expected to execute ships with the slate table directly above its code block (contract below); the code block stays pure prompt. After the last slate of the delivery: the **risk register** `| Shot | Kept risk | List (red/yellow, renderability §2) | Why kept | Rescue |`, one row per kept red/yellow element. A treatment carries risk and rescue in its shot-table columns; the bible shot board's `Risk → rescue` cell is canon for both.
12. **The production bible is canon** (ch. 22, template 22b). ONE living bible per project, created before the first asset order — even for a job that looks like a single session. Resume: read it first; close: update it last. Statuses move only on director approval. Before it exists, canon = the treatment or script the director approved in this conversation, recorded at the first close; once it exists: not in the bible = not canon.
13. **Repair before reroll (Seedance 2.5).** An approved take with a local fault is fixed with the edit suite — region/timestamp-scoped, camera-perspective, green-screen, audio-category edits — or extended, never regenerated wholesale (ch. 14b, W5). The production take is a NEW generation of the locked prompt at target resolution and full planned duration, never a `video_extension` of the draft; from then on every fix to it is an edit or an extension.
14. **Canon before invention — never guess story content.** Every content claim in a prompt is READ from the treatment, script or bible for that exact beat, then checked once against scene physics and story logic; every prompt is re-read against its canon passage before delivery.
   - *Canon-bound — never guessed:* what happens in the beat · who is present and where · dialogue/VO text · prop and wardrobe STATE changes · time of day, weather and light state where plot or continuity fixes them · anything that changes the story.
   - *Craft-fillable — only WHEN a line is needed:* the shot-size word · the one camera line · look controls (rule 7) · light direction within the plate's light side · micro-cues for the stated emotion · blocking inside the stated geography · diegetic sound — each listed in `Crew choices` for the director's veto.
   - Canon silent on a canon-bound item → ship a `PROPOSAL — not canon` block in that prompt's place (shape below), continue with the rest of the batch, never fill the gap. Approval = an explicit yes or a picked option (22a rule 3); "go on" is not — ask once, naming the options. Treatments, scripts and shot lists are the agent's DRAFT until approved — a prompt written from one says so in its `Intent` row.
   ```
   PROPOSAL — not canon · Shot 1B · the treatment does not say how the cat reaches the lever
   A) the cat climbs the coiled rope beside the lever (uses the rope in @loc_lamproom, plants nothing new)
   B) the wind slams the hatch and the cat is thrown toward the lever (needs a plant in 1A)
   Pick A or B, or give the beat — the prompt follows.
   ```
15. **Prompt first, model last.** Most presumed "model limits" are prompt faults [PP]. Before blaming the model, switching method or cutting the shot, lint YOUR prompt — over-instruction first, then contradictions, a missing lock on exactly the failing aspect, stacked instructions on one axis (they average, not add), meta-commentary.
   - One iteration = one prompt revision judged on ONE batch of 4 rolls: one or two odd rolls = reroll, do not touch the prompt; three or four bad rolls on one axis = failed iteration (production-pipeline ch. 10).
   - Repair per iteration, one line each: REMOVE (sentences on model-owned axes, second mentions) → CHANGE one line → ADD one line; the word count never rises.
   - After the 3rd failed iteration: rewrite short from scratch — never longer than the prompt that failed — AND move the failing aspect to a stronger channel: reference, sketch, mask, seed, other model (24b item 7). A model limit only after that clean prompt has failed twice on at least two channels → other model (renderability §6) or the shot's rescue path. Budget 10–15 iterations per shot; then simplify the SHOT — split it, drop an action, change the angle — not the words.
16. **The causal chain is load-bearing — no event without cause, no rescue without plant.** Every event is CAUSED by what precedes it and CAUSES what follows ("therefore/but", never "and then"); coincidence may create trouble, never resolve it; every payoff is planted. Before proposing ANY script, treatment or beat change, run the causal change lint (ch. 23g) and name the change's upstream cause and downstream consequence IN the proposal.
17. **Version receipt before an external generation.** Every UI/MCP/API recommendation and every stored platform fact carries the project KEY (RECEIPT line in bible section B1b) in exactly one state: `live-checked <date>` — you or the director read the live form or schema in THIS session; only then may a new date, price or account appear · `from reference <KEY>` — no live read this session: cite the newest stored receipt with ITS check date, account and cost left empty. A from-reference slate is a complete, valid deliverable; a live-checked date for a check you did not perform is fabrication. Never gate drafting on a live value.

## The per-prompt checklist — every new still or video prompt, edit or extension, in this order

1. **CANON** — read the treatment/script/bible passage for this exact beat or asset; a canon-bound gap → rule 14.
2. **ROUTE** — platform, surface, model and mode BEFORE writing; mint or reuse the project KEY with its receipt state (rule 17). Stills: model matrix (production-pipeline ch. 5) + style mechanics (style-control §2–4). Seedance 2.5: `t2v` / `omni_reference` / `video_edit` / `video_extension`, written as `id ("UI label")` per the mode table in platform-ui-workflows §1 — and first ask: is this a repair or extension of an existing take (rule 13)?
3. **REFERENCES** — one reference per element that must persist, pulled from the pool by exact tag, one *reference line* each in the technique's shape (glossary), counted against rule 5's ceiling.
4. **WRITE** — in the project's technique and the model's container (rule 4), in generator logic (rule 6): describe, don't argue; positive first; one instruction per axis; must-have element first; relations, not measures (rule 7); nothing on a model-owned axis unless deliberately steered.
5. **LINT** — still: the eight checks of ch. 24i. Video: the seven measures into the slate's `Lint` row (format: slate contract; definitions: the "Lint before delivery" paragraph of ch. 12h — shared by every technique; reading that one paragraph is not opening a second technique chapter); a failed measure is repaired, never delivered with a justification. Then the red-list lint with a rescue for every kept risk (rule 8) and the canon re-read — fix or flag (rule 14).
6. **DELIVER** — the Render Slate above the code block, then the risk register (rule 11).
7. **AFTER THE RESULT** — review in six passes, in this order: identity → continuity → timing → camera → audio → style (the take-level checks of the project's Verify line; verdict order post-audio-legal ch. 19). A result you cannot see is never described: put the six passes to the director as questions and record THEIR answers as the review (`director review, TK03`); without one the take keeps its status (`TKnn — review pending (director)` in the bible Handoff). A local fault on an approved take → W5; a global fault, or a model without a scoped edit route → back to the prompt in the rule-15 order.

| `Lint` | Every video prompt, in any technique: `words n · negations n/1 · numerals outside TC n/0 · absolute measures n/0 · double mentions none · contradictions none · beats complete` (definitions and counting rules: ch. 12h; `words` is a count for the rule-15 ratchet, never a ceiling; each numeral exception is a look control named in Crew choices) |
| `Inputs` | One line per reference, numbered in slot/upload order: `n. @tag = what it is — its one job`; say whether the anchor is a reference or a literal start/end frame (rule 1); on a platform with a persistent library say "Elements, no upload"; add `🟡 token form unverified — match the upload label before running` when the surface could not be seen (ch. 12b) |
| `Store in` | Known platform project/folder or local destination — omit rather than invent |
| `Handoff` | Linked work only: an extension boundary state, an edit source + scope (`edit source …__T2V__P01__TK03`), a continuity boundary |

**ID discipline.** The Shot ID is project canon from the shot board (`1A`, `SQ03_SC12_12A`) — never invent sequence or scene data; without a board, `<scene><letter>` in delivery order and the delivered shot table IS the board. The Render ID appends platform-model, operation and prompt revision (`…__HF-SD25__T2V__P01`; a rewrite is `P02`); a Take ID (`TK01` …) exists only once a generated result exists — in the bible and review notes, never in a slate. No title yet → ask once and hold the row, never a placeholder; a one-off prompt outside any project omits the row and says so. Full grammar — tokens, variants, asset prompts, multi-shot takes, instance chain, first-session bootstrap: production-bible 22e; read it before a project's first Render ID.

## Workflow

1. **Intake** — run W1 (`workflows.md`), then settle only what the conversation has not settled — format and look, length and platform, deliverable, model stack, prompting technique (rule 4), dialogue language and its route (ch. 18; default native, proven by one draft-resolution test take) — then the bible (W1 step 5). **Interaction contract** (full text: W1 step 3): before the first deliverable at most ONE grouped question message — the story-gate gaps plus the open intake items; everything unanswered ships on a labelled default, marked `ASSUMED` where it appears and logged in the bible decision log. "Just do it" or an unavailable director → proceed on ASSUMED values, canon-bound gaps as PROPOSALs (rule 14); afterwards one question at a time, only when a canon-bound item blocks the next step.
2. **Write shot-first, canon-first** — re-read the canon passage before every beat (rule 14); a treatment or shot list that is itself the deliverable is a DRAFT proposal from the intake, asking only for story gaps (23a), never per beat. Numbered shots, a fixed camera grammar per sequence, object-anchored blocking (never screen directions), @asset names, match-action cues (shot-writing grammar and dialogue scenes: production-pipeline ch. 2 and ch. 7).
3. **Lint** against `renderability.md`; rewrite or rescue every hit.
4. **Pre-production sections in the treatment** — build order, set build and casting per production-pipeline ch. 1, 3 and 4; the style contract = one bible paragraph derived from the recipe, never pasted as-is: stills → the model's style section (style-control §2–5); technique A → the 8–10 STYLE tokens (ch. 12h); B → distributed into the blocks (ch. 12 placement rule 1); C → the Master Style Block (§6c).
5. **Deliver** per the routing table's file for the format — treatments end each scene with its shot table; its Shot IDs ARE the bible shot board's IDs, assigned once and never renumbered (the board mirrors Shot, Len and Risk → rescue; Framing, Action and Assets stay in the approved treatment):
   `| Shot ID | Len | Framing | Action | Assets | Risk | Rescue |`
   `| 1A | 4 s | medium-wide, static, low, from the room corner | wet cat squeezes through the hatch, shakes, looks up at the dark lamp | @cat @loc_lamproom @anchor_1A | 🟡 wide opening (stylized 3D) | open on the medium, arrive at the wide by transition |`
   Framing = shot size, camera height/direction and move in words, never degrees or lens values (rule 7); Len = planned seconds inside the take; Assets = @tags only. Close every work block by updating the bible (rule 12; create it now if this block ordered assets and none exists).
